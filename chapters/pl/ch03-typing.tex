\chapter{Typowanie: adnotacje, checkery i gdzie checker kłamie}
\label{ch:typing}

\chapterstub{%
\textit{[Opis do przetłumaczenia --- patrz wydanie angielskie.]}

Argument: a type hint is a claim the runtime never checks, and a checker is
a second compiler you have to invite. The map: hints against the C\# type
system (gradual against static, structural against nominal); \code{Protocol}
against an interface; \code{dataclass}, \code{TypedDict}, \code{NamedTuple}
and a pydantic model against a record, a DTO and a POCO; \code{T | None}
against nullable reference types; generics in the PEP 695 syntax against C\#
generics, variance included; \code{Literal} and \code{Enum};
\code{TypeGuard} and \code{TypeIs}; \code{Any} against \code{dynamic} and
\code{object}. Where the checker lies: \code{Any} propagation, untyped
third-party packages, \code{cast}, \code{type: ignore}, and JSON arriving at
a boundary \dash{} which is why pydantic exists, and where the LangChain
book's chapter 2 stops. pyright against mypy: which to run in CI and why
this book pins both. Payoff: a strictness configuration the reader can copy,
and one rule \dash{} validate at the boundary, trust inside. Traps to
elicit: nullable-reference-type thinking (\code{str} can be \code{None} at
run time and nothing will say so); \code{List[int]} from a 2019 tutorial;
assuming \code{@dataclass} validates; a mutable default argument. Listings:
the same DTO four ways; a \code{Protocol} satisfied by a class that has
never heard of it; a checker false negative reproduced on the pinned
checker. Four exercises. Deferred: pydantic in depth belongs to chapters 9
and 13.
