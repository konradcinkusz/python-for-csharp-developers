\chapter{CPython, the GIL and the free-threaded build}
\label{ch:runtime}

\noindent
You already have a runtime model. A process hosts one runtime, IL is
compiled ahead of time and then compiled again by a JIT on first call, and a
thread pool turns four cores into four times the work. It is a good model,
it is why you are productive, and three of those four sentences are wrong
here. They do not fail together, either: they stop holding one at a time,
each has a name, and each has a one-line question you can put to the
interpreter in front of you.

That is the method for this chapter and for the book. Nothing below is a
fact you are asked to take on trust: every one is a line you can run, and
every listing prints its answer out of the running process rather than
carrying it as a string.

Run it and the pinned interpreter says:

\transcript{ch01-interpreter}

\noindent
Four of those five will change over the next four sections. The one to read
now is the fourth. \api{sys.\_jit} is new in \pyver, it reports that this
binary was compiled \emph{with} a just-in-time compiler, and it reports that
the compiler is switched off. Both halves matter. There is a JIT, so
somebody who tells you Python has none is out of date; it is off by default,
so anybody reasoning about your production latency as though a JIT were
warming up is wrong about the process they are looking at.

\begin{versionbox}
The \pyver{} JIT (PEP~744) is experimental and opt-in, and CPython's own
release notes say it is not recommended for production. \code{PYTHON\_JIT=1}
sets the enabled flag; the interpreter above then reports \emph{available}
and \emph{enabled} together. A binary can be built to carry the compiler
with the flag off, which is what the pinned interpreter is and why the two
answers differ. This book has not measured what it does to a workload;
CPython's own estimate of the range, which is the honest one to quote, is
anywhere from somewhat slower to somewhat faster depending on what you run.
\end{versionbox}

\begin{csbox}
\code{sys.\_is\_gil\_enabled()} and \code{sysconfig.get\_config\_var} are the
nearest thing to \code{RuntimeInformation.FrameworkDescription}: they
describe the host, not your code. The difference is that in Python the
answers are load-bearing. Two of them decide whether a thread pool is the
right tool.
\end{csbox}

\section{There is a compile step, and it has a cache}
\label{sec:ch01-bytecode}
\index{bytecode}\index{bytecode!\_\_pycache\_\_}

\noindent
Before you read on, answer this from your current model. You have
\code{app.py}, which imports \code{helper.py}. You run \code{python app.py}
twice in a row. How many times is each of the two files compiled?

\medskip
\noindent
Python compiles source to bytecode before it executes anything, exactly as
\code{csc} compiles to IL. The difference is when, and where the result is
kept. The compiler runs on import, the result is written next to the source
in a \code{\_\_pycache\_\_} directory, and \pkg{dis} in the standard library
reads it back.

\pyregion{code/ch01/bytecode.py}{function}{Four lines of source, and the compiler has something to say about each}{lst:ch01-function}

\noindent
\code{dis.dis} on that function prints the bytecode the compiler produced,
with the source line each instruction came from down the left:

\transcript{ch01-bytecode}

\noindent
So the answer to the question above is \emph{twice, and once}.
\code{helper.py} is imported, so it is compiled once and the result is
cached; every later run reads the cache. \code{app.py} is the file you named
on the command line, and the module named on the command line is never
cached \dash{} it is compiled from source on every run. That is a small
amount of work you pay for each time, and it is why a large script feels
marginally slower to start than the same code behind an import.

\begin{trapbox}
\textbf{\enquote{Python has no compile step, so there is nothing like IL.}}
There is a compile step, it produces bytecode, and the bytecode is cached on
disk where you can see it. What Python does not have is a compile step you
must run, or a build artefact you ship instead of the source. The
\code{\_\_pycache\_\_} directory is a cache and nothing else: delete it and
the next run rebuilds it, ship it and the next interpreter may ignore it,
and \code{python -B} skips writing it altogether.
\end{trapbox}

\mermaidfig{ch01-compile-step}{The same two steps in both languages, at different times and into different places}{source to bytecode, source to IL}

\begin{note}
The cache file is named for the interpreter that wrote it \dash{}
\valtext{e01.default.tag} on \pyver{} \dash{} so two versions can share a
directory without reading each other's bytecode. The tag comes from
\code{sys.implementation.cache\_tag} and the path from
\code{importlib.util.cache\_from\_source}, which is what the listing prints
rather than assembling the path itself.
\end{note}

\begin{exercise}{e01_01_disassemble}{Read the bytecode of a function you wrote}
Implement \code{instruction\_names}, which takes a function and returns the
names of the opcodes it compiled to, in order. The test disassembles two
functions of its own and checks the answer, so it has to come from the
function object rather than from a list you typed. Note what the test does
\emph{not} do: it never calls either function. The bytecode exists as soon
as the module is compiled.
\end{exercise}

\section{A module, an assembly, and what \code{\_\_main\_\_} is for}
\label{sec:ch01-main}
\index{module}\index{sys.path@\texttt{sys.path}}

\noindent
A module is a file. An assembly is a deployment unit that may hold hundreds
of types from dozens of files, and it carries a manifest. Almost every
difference in this section comes from that one.

There are two ways to start a program, and they are not interchangeable:

\begin{shellcmd}
python pkg/mod.py     # by path
python -m pkg.mod     # by module name
\end{shellcmd}

\noindent
Both set \code{\_\_name\_\_} to \code{"\_\_main\_\_"} in the module they
start. They differ in what goes on the import path. The first puts the
script's own directory there, so \code{pkg/} is on the path and
\code{import pkg} fails. The second puts the current directory there, so
\code{pkg} is importable and the module is found through the import system
\dash{} which is also why, under \code{-m}, the file you named gets a cache
entry and, under a path, it does not.

\begin{csbox}
\code{python -m pkg.mod} is the nearest thing to \code{dotnet run}: you name
the thing, not its file, and the runtime resolves it. \code{sys.path} is
assembly probing, except that it is an ordinary list of strings you can
print, mutate and get wrong. There is no manifest, no strong name and no
GAC; there is a list, and the first match wins.
\end{csbox}

\begin{trapbox}
\textbf{\enquote{\code{if \_\_name\_\_ == "\_\_main\_\_"} is boilerplate.}}
It is the only thing standing between a module that can be imported and a
module that runs its program when anything imports it. A test suite imports
your file to get at one function; without the guard it also runs your
\code{main}. With the guard, the same file is both a library and a program,
which is why every listing in this book has one.
\end{trapbox}

\begin{exercise}{e01_02_entrypoint}{One file, a module and a program}
Finish \code{main} and add the guard. The test imports the module and
insists nothing has run, then calls \code{main} and insists it has, then
runs the same file as a program in a subprocess and insists it printed. One
of those three fails on the starter for a reason worth noticing: the import
half passes on an unfinished file, so it cannot be a test of its own.
\end{exercise}

\section{One lock, and what it actually locks}
\label{sec:ch01-gil}
\index{GIL}\index{GIL!what it serialises}\index{threads}

\noindent
One CPython process is one interpreter with one lock. A thread must hold
that lock to execute bytecode, so on the default build exactly one thread
is running Python at any instant, however many cores you bought.

Before the numbers: four threads, four cores, each thread running the same
pure-Python arithmetic loop. Against one thread doing one loop, how long do
you expect the four to take?

\medskip
\noindent
The listing times three kinds of work on one thread and on four. The
workloads are these, and the third is the one people do not predict:

\pyregion{code/ch01/workloads.py}{cpu}{Pure Python: every step of this holds the lock}{lst:ch01-cpu}

\pyregion{code/ch01/workloads.py}{digest}{The same shape of work, done inside a C extension instead}{lst:ch01-digest}

\pyregion{code/ch01/workloads.py}{io}{A real socket read, rather than a sleep: the thread is parked inside recv}{lst:ch01-io}

\noindent
Experiment E1 runs that file on both builds. On the default build, on
\valtext{e01.machine}, with \val{e01.threads} threads:

\begin{center}
\small
\begin{tabularx}{\linewidth}{@{}Xrrr@{}}
\toprule
\textbf{Workload} & \textbf{1 thread} & \textbf{4 threads} & \textbf{ratio} \\
\midrule
\code{cpu}, pure Python & \val{e01.default.cpu.one}\,s & \val{e01.default.cpu.many}\,s & \val{e01.default.cpu.ratio}$\times$ \\
\code{io}, socket read & \val{e01.default.io.one}\,s & \val{e01.default.io.many}\,s & \val{e01.default.io.ratio}$\times$ \\
\code{digest}, C extension & \val{e01.default.digest.one}\,s & \val{e01.default.digest.many}\,s & \val{e01.default.digest.ratio}$\times$ \\
\bottomrule
\end{tabularx}
\end{center}

\noindent
Four threads of pure Python take \val{e01.default.cpu.ratio} times as long
as one. They did not run in parallel; they ran one after another, and paid
for the switching. The other two rows cost nothing at all, and for the same
reason in both cases: a thread parked in \code{recv} is not executing
bytecode, and neither is a thread inside \pkg{hashlib}, which releases the
lock around the work and takes it back afterwards.

\mermaidfig{ch01-one-lock}{The lock is held while bytecode runs and dropped everywhere else}{what the lock serialises}

\begin{trapbox}
\textbf{\enquote{Threads are useless in Python, so I will not bother with
them.}} Two of the three rows above say otherwise. The lock serialises
\emph{bytecode}, and a thread that is waiting on a socket, a file or a
database, or that is inside a C extension doing the work in C, is holding
nothing. Threads are the right tool for I/O-bound work and the wrong one for
CPU-bound work, and that is a statement about the workload rather than about
threads.
\end{trapbox}

\begin{note}
The consequence of this lock for an event loop \dash{} one blocking call
inside \code{async} code freezing every other coroutine, with no error and
no log line \dash{} belongs to the companion volume, \emph{LangChain,
LangGraph and Async Python}, which measures it in its Chapter~3. This
chapter owns the runtime model and stops here.
\end{note}

\section{The free-threaded build is a different binary}
\label{sec:ch01-freethreaded}
\index{free-threaded build}

\noindent
You have read that \pyver{} removed the lock. Look back at the transcript in
\S\ref{sec:ch01-questions}: it was produced by \pypatch, and it says the
lock is on. Which of the two statements is wrong?

\medskip
\noindent
Neither. Free-threaded CPython is PEP~703, it arrived one version before
this one as an experiment, and PEP~779 made it a supported build option in
\pyver{}. \emph{Supported build option} is the whole sentence: there are two
binaries. The one almost everybody
installs, and the one this book pins, is the default build with the lock.
The other is \code{python\pyver{}t}, built separately, installed separately, and
distinguished by the \code{t} in \code{sys.abiflags} \dash{} which is where
its name comes from. Running the same listing under each gives:

\begin{center}
\small
\begin{tabularx}{\linewidth}{@{}Xll@{}}
\toprule
& \textbf{\code{python\pyver{}}} & \textbf{\code{python\pyver{}t}} \\
\midrule
version reported & \valtext{e01.default.version} & \valtext{e01.freethreaded.version} \\
free-threaded build & \valtext{e01.default.ft} & \valtext{e01.freethreaded.ft} \\
GIL enabled right now & \valtext{e01.default.gil} & \valtext{e01.freethreaded.gil} \\
JIT available / enabled & \valtext{e01.default.jit} & \valtext{e01.freethreaded.jit} \\
bytecode cache tag & \valtext{e01.default.tag} & \valtext{e01.freethreaded.tag} \\
\bottomrule
\end{tabularx}
\end{center}

\noindent
Two rows there are worth stopping at. The two builds report the same cache
tag, so they read and write the same \code{\_\_pycache\_\_} files: the
bytecode is identical and only the runtime beneath it differs. And the JIT
is not merely off on the free-threaded build, it is not there. That is not
an accident of this binary: CPython's release notes for \pypatch{} say
free-threaded builds do not support JIT compilation, so the two \pyver{}
experiments do not compose.

Now the same three workloads again, on \code{python\pyver{}t}:

\begin{center}
\small
\begin{tabularx}{\linewidth}{@{}Xrrr@{}}
\toprule
\textbf{Workload} & \textbf{1 thread} & \textbf{4 threads} & \textbf{ratio} \\
\midrule
\code{cpu}, pure Python & \val{e01.freethreaded.cpu.one}\,s & \val{e01.freethreaded.cpu.many}\,s & \val{e01.freethreaded.cpu.ratio}$\times$ \\
\code{io}, socket read & \val{e01.freethreaded.io.one}\,s & \val{e01.freethreaded.io.many}\,s & \val{e01.freethreaded.io.ratio}$\times$ \\
\code{digest}, C extension & \val{e01.freethreaded.digest.one}\,s & \val{e01.freethreaded.digest.many}\,s & \val{e01.freethreaded.digest.ratio}$\times$ \\
\bottomrule
\end{tabularx}
\end{center}

\noindent
The first row is the whole experiment. Four threads of pure Python now cost
\val{e01.freethreaded.cpu.ratio} times one thread rather than
\val{e01.default.cpu.ratio}, and the same work finishes
\val{e01.cpu.wallclock.gain} times sooner in wall-clock terms. Nothing about
the code changed; the interpreter did.

\begin{warning}
Read both tables with the spread in mind. No ratio here held steadier than
about \val{e01.spread} per cent across the \val{e01.repeats} runs behind each
row, so there are two answers in these six rows rather than six: everything
at about \val{e01.freethreaded.cpu.ratio}, and the single row at
\val{e01.default.cpu.ratio}. The absolute times belong to
\valtext{e01.machine} on \valtext{e01.recorded}; the ratios are what
transfers, because they follow from the lock rather than from the hardware.

There is one number here this experiment reports and declines to conclude
anything from. What does free-threading cost a single thread? It is the first
thing everyone asks. The two one-thread columns differ by
\val{e01.cpu.singlethread.diff} per cent, and CPython's own release notes for
\pypatch{} put the single-threaded penalty at roughly five to ten per cent,
depending on platform and compiler \dash{} so the two agree, and the
agreement is worth nothing, because \val{e01.cpu.singlethread.diff} per cent against a
\val{e01.spread} per cent spread is not a measurement. Across recordings on
this machine the same difference has come out at one, seven and eleven per
cent. A quieter machine and a workload sized for that question alone would
settle it; until one is run the figure to quote is theirs and not this
book's.
\end{warning}

\mermaidfig{ch01-two-binaries}{One version number, two binaries, and one bytecode cache between them}{two builds, one bytecode cache}

\begin{trapbox}
\textbf{\enquote{\pyver{} is free-threaded now, so the GIL is gone.}} It is
gone in a build you have to ask for. \code{uv python install \pyver{}t} fetches it; \code{python\pyver{}t} runs it; and until you have typed one
of those, every process on the machine still has the lock. The build and the
process are separate questions, too: run \code{python\pyver{}t} with
\code{PYTHON\_GIL=1} and you get a free-threaded binary with the lock turned
back on, which is why the listing in \S\ref{sec:ch01-questions} asks both.
\end{trapbox}

\section{The decision this buys you}
\label{sec:ch01-decision}
\index{threads!choosing a pool}

\noindent
Four rows of measurement collapse into one rule you can apply without
measuring anything again: \textbf{the lock costs you exactly when several
threads are all running Python bytecode}. Everything else \dash{} waiting on
the network, waiting on a disk, waiting on a database, or spending the time
inside a library written in C \dash{} is already parallel, and was before
\pyver{}.

So there is one cell in the table where threads are the wrong answer, and on
the default build it is answered with processes, which have a lock each.
That is what the last exercise asks you to write down.

\begin{exercise}{e01_03_which_pool}{Threads or processes, and on which build}
Implement \code{pick\_pool}, which takes one of three workload kinds and
returns \code{"threads"} or \code{"processes"}. It takes the build as a
parameter, defaulting to whatever the running interpreter reports, so the
test can put both builds to you without your having two installed. Only one
of the six cells says processes, and the exercise is knowing which.
\end{exercise}

\noindent
Two threads of that rule are picked up later. Chapter~\ref{ch:asyncio} does
the same work with one thread and an event loop, which is a different answer
to the same question about waiting. And the reason a process is the
expensive escape hatch \dash{} that it is a separate interpreter with a
separate memory space and a serialisation cost at the boundary \dash{} is a
packaging question before it is a concurrency one, which is where the next
chapter starts.
