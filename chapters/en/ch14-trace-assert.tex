\chapter{trace-assert, complete: the same instrument in three languages}
\label{ch:traceassert}

\noindent
An agent run is expensive to judge and cheap to check. Judging it needs
another model, a rubric, a budget and an argument about whether the judge
agrees with a human. Checking it needs the run's own record and a function
that reads it \dash{} and most of what goes wrong with agents in production
is visible in that record without anybody forming an opinion about the
prose.

This chapter finishes \code{trace-assert}: the trace model, the full
assertion set, and the package. By the end you will have built in Python
what you could already have built in C\#, and the last section of the
chapter is the comparison, because the same design exists in three
languages and the three turn out not to carry the same thing.

\section{The cheapest evaluation an agent can have}
\label{sec:ch14-cheapest}
\index{evaluation!deterministic}

Before reading on, answer this for yourself: what does it take to run an
evaluation over an agent? Most answers name a model \dash{} something has
to read the reply and decide whether it was any good.

\begin{trapbox}
\textbf{A trace assertion needs a model to evaluate.} It does not, and the
assumption is what keeps most teams from having any evaluation at all,
because a suite that needs a provider needs a budget, a key and a network,
and so it does not run on a pull request. \emph{Did the agent call the tool
it was told to? In the order it was told to? With an identifier that came
back from an earlier call? Without calling the one it was forbidden?}
Every one of those is decidable from the recorded run. Appendix~\ref{app:traps}
keeps this entry, and it is the reason this layer exists.
\end{trapbox}

\noindent
So there are two layers, and they are not competitors. The deterministic
layer grades the machinery \dash{} what was called, in what order, with
what. The judged layer grades the quality of the sentence the user reads.
This chapter builds the first. It is the one that can block a merge,
because it costs nothing and gives the same answer twice.

\begin{csbox}
An xUnit engineer has built this before without calling it evaluation: it
is an integration test that captures what the system under test did and
asserts over the capture rather than over a return value. What is new is
the subject, not the technique \dash{} and the reason to give the capture a
name and a shape is that a dozen assertions over it want the same
questions answered.
\end{csbox}

\section{A trace is not a log}
\label{sec:ch14-trace}
\index{trace!model}

The obvious model for a run is a list of events with a kind on each, and it
is what the first version of this package had. It fails on the first
interesting question. \emph{Did the write happen before the approval?} is a
comparison between a tool call and a contract event, and a single list with
a discriminator has no ruler to compare them on until you invent one.

So the model is the one \code{agent-eval-bench} arrived at: three parallel
records, with tool calls and events sharing one position index.

\pyregion{code/src/trace_assert/trace.py}{model}{The three records a trace is made of}{lst:ch14-model}

\noindent
Three decisions in there are worth naming, because each is a defect
somebody has shipped.

\textbf{A tool call is one call, however many transport attempts it took.}
A resilience handler that retries twice underneath the agent has not made
three calls; an orchestrator loop that calls the tool again has. Those are
different numbers answering different questions, and a model that conflates
them cannot tell a retried request from a double booking.

\textbf{A call exists whether it succeeded or not.} If a failed write left
no record, \emph{the write was never attempted} and \emph{the write failed}
would look the same in the evidence, and they are the two outcomes a
degradation test exists to distinguish.

\textbf{Nothing here lets an assertion read the agent's prose} except
\code{Turn.reply}, which is there so that one assertion can search it for
leaked identifiers. The moment an assertion matches text like
\enquote{I have booked}, every rewording of a prompt becomes a failing
test, and the suite starts grading phrasing.

\section{The twelve, in three families}
\label{sec:ch14-twelve}
\index{trace!assertions}

There are \val{ta.assertions} assertions, and the number is not this
book's: it is the count in \code{agent-eval-bench}'s own schema, and the
list was copied from it rather than recalled. Adding a thirteenth here
would make it a thirteenth that two other ports of the same design do not
have.

\mermaidfig{ta-three-families}{The \val{ta.assertions} assertions, in the three families the specification groups them into}{the three assertion families}

\noindent
Presence and absence are the halves people get wrong together. A test that
proves an agent refused must assert both the refusal \emph{and} that the
forbidden call never happened: an agent that apologises politely and then
calls the tool anyway passes the first assertion on its own.

\pyregion{code/src/trace_assert/assertions.py}{presence}{Presence and absence, which are always written as a pair}{lst:ch14-presence}

\noindent
The shape family is where the interesting ones live, and \code{order} is
the one whose specification has to be read carefully. It does not compare
the earliest occurrence of one thing with the earliest of another. Every
occurrence of the second must come after the \emph{first} occurrence of the
first \dash{} because the weaker reading lets a write slip in ahead of the
gate so long as a second, well-behaved write follows it, and the gate is
about the first one.

\pyregion{code/src/trace_assert/assertions.py}{order}{\code{order}, and the reading that looks equivalent and is not}{lst:ch14-order}

\begin{exercise}{e14_01_called_with}{Port one assertion}
\code{tool\_called\_with} asks whether some call carried the arguments you
named, under one of two readings: \code{subset} allows other arguments,
\code{exact} does not. Write it. The test asks for both readings, for a
failure message that names what was found, and for the case that separates
a real assertion from a decorative one \dash{} a tool that was never called
has to fail rather than pass for want of a counterexample.
\end{exercise}

\section{Three disciplines, and one of them is load-bearing}
\label{sec:ch14-disciplines}
\index{evaluation!vacuous assertion}

The \val{ta.assertions} functions share three rules. The first is the one
above: nothing matches prose. The third is small \dash{} an argument that
cannot be used is an error rather than a pass, which matters here because
the C\# port has a JSON schema in front of it to refuse a malformed
assertion and this one has nothing but itself.

The second is the one worth the section.

\begin{trapbox}
\textbf{No assertion may pass vacuously.} Write
\code{call\_attempts} the obvious way \dash{} take the largest attempt
count over the calls to that tool, fail if it exceeds the bound \dash{} and
it is green on a run where the tool was never called at all, because the
maximum of nothing is zero and zero is under every bound. A suite asserting
restraint then passes on the run in which nothing happened, which is the
one run it should be loudest about.
\end{trapbox}

\pyregion{code/src/trace_assert/assertions.py}{attempts}{Most of it is the guard against passing on a run where nothing happened}{lst:ch14-attempts}

\noindent
The same rule decides \code{order} when either side never occurred,
\code{tool\_called\_with} when the tool was never called, and
\code{argument\_grounded} \dash{} which is the assertion that earns the
whole layer its place, because it catches a confidently invented identifier
that no judge reliably will.

\noindent
The guiding project's own suite is \val{ta.tests} tests over the

\begin{csbox}
The C\# port returns an outcome record from each assertion instead of
raising, and that is not a language difference \dash{} it is a difference
in what the harness has to do. It grades a whole corpus and reports a pass
rate against a recorded baseline, so it needs every result, including the
ones that failed. In Python the test framework collects that for you, so
an assertion that raises is the shorter and more idiomatic shape.
\end{csbox}

\section{The same trace in three languages}
\label{sec:ch14-ports}
\index{trace!ports}

The design exists three times, and the comparison is not the one the
chapter title promises without qualification. \textbf{What is in three
languages is the trace model.} The layer built on top of it is different in
each.

\mermaidfig{ta-three-ports}{One model, ported twice, carrying a different layer in each language}{what each port actually carries}

\begin{center}
\small
\begin{tabularx}{\linewidth}{@{}lXXX@{}}
\toprule
 & \textbf{.NET} & \textbf{TypeScript} & \textbf{Python} \\
\midrule
Layer & assertions and judge & judge only & assertions only \\
Types & records, nullable reference types & \pkg{zod} schemas, parsed at the edge & frozen dataclasses, \pkg{pyright} strict \\
Async & none needed; the trace is in memory & the worker is a queue consumer & none needed \\
Framework & xUnit v3, one test per scenario & \pkg{vitest} & \pkg{pytest}, one test per claim \\
Refusal & a JSON schema rejects a bad assertion & the schema parses at the edge & the function raises \\
Packaging & a project reference, never published & private, deployed as a container & a wheel on an index \\
\bottomrule
\end{tabularx}
\end{center}

\noindent
Two things fall out of that table and neither was expected before the three
repositories were opened.

The first is that \textbf{the thing that travels is the data shape, not the
code}. Each port re-implements its layer in the idiom of its language and
none of the implementations resembles another; what is identical is the
record the layer reads, down to the shared position index. A design that
travels is a design whose interface is a value.

The second is about where a contract can live. The .NET port refuses a
malformed assertion with a JSON schema, because its assertions arrive from
YAML files written by hand. The Python port has no file in the loop, so the
same refusal has to be code, and the function raises \code{ValueError}
where the schema would have. Neither is more careful than the other; the
care is in the same place in the pipeline either way.

\begin{note}
This chapter's brief, and the book's introduction, describe the comparison
as three ports of one instrument. That is true of the trace and not of the
assertions, which exist in .NET and in Python. The TypeScript port is
\code{judge-worker}, and it carries the rubric judge rather than this
layer; its own trace types say in a comment that they were ported from the
same C\# file. The brief has been corrected rather than the chapter written
to it.
\end{note}

\section{Publishing it}
\label{sec:ch14-publish}
\index{packaging!uv build}

\code{uv build} is one command, and it is not the part worth a page. What
is worth a page is what came out of it, because that \dash{} and not the
code \dash{} is what somebody installs.

\noindent
A wheel is a zip file with a metadata member in the format of an email
header block, which is why it is parsed rather than split on colons: the
format has repeated fields, and a dictionary keeps only the last of
the repeated \code{Requires-Dist} lines. Run against this book's own
project, it reports:

\transcript{ch14-publish}

\noindent
Which is the honest finding of this section. The book's \code{code/}
directory builds a distribution named after the book, pinned to the one
Python minor the book is built on, declaring a row of runtime
dependencies that \code{trace\_assert} imports none of. It is a fine project for holding
fourteen chapters of listings and it is not a package anybody should
install. What you publish is a project, and a project is its metadata.

The publish itself is then two commands and no secret:

\begin{shellcmd}
uv build
uv publish --trusted-publishing automatic
\end{shellcmd}

\noindent
Trusted publishing means the index verifies the workflow that is uploading
rather than a token somebody pasted into a settings page: there is no
long-lived credential to leak, and a fork cannot use it. The one-time
configuration is on the index's side, outside any file in this repository,
and it has not been done for this book's own copy \dash{} that is an open
issue rather than a step this chapter can show you completing.

\begin{exercise}{e14_03_publishable}{Make it publishable}
Write the \code{[project]} table a published \code{trace-assert} needs. The
test parses it and asks seven things of it; read the test, because it is the
specification. Two of the seven are the ones this section measured: the
package must declare no runtime dependencies, because every import in it is
from the standard library, and it must admit more than the one Python minor
the book happens to be built on. A third is the one
Chapter~\ref{ch:testing} promised: the \code{trace} fixture arrived there
through a line of \code{conftest.py}, and a package cannot ask its users
for that line.
\end{exercise}

\section{What you have}
\label{sec:ch14-what}

A package, which is an artefact somebody can install. A design you can
describe in an interview in two sentences \dash{} \emph{a trace is three
records on one index, and twelve functions read it} \dash{} and defend
against the obvious objection, which is that it does not grade quality and
was never meant to. And a piece of Python that a C\# engineer would
recognise line for line, written in the idiom of the language rather than
in a translation of theirs.

That was the whole claim of the book. The mapping tables are in
Appendix~\ref{app:cheatsheet}; the habits that cost you an afternoon are in
Appendix~\ref{app:traps}; and everything under \code{code/} runs.
