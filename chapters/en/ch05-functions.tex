\chapter{Functions and control flow: decorators, comprehensions, generators, context managers}
\label{ch:functions}

\noindent
Python's control-flow vocabulary maps onto C\#'s feature for feature. A
decorator is middleware, a comprehension is a LINQ query, a generator is an
iterator block, \code{with} is \code{using}, \code{match} is a switch
expression. The mapping is close enough to be worth making and loose enough
to be worth checking, and this chapter is about the places where it slips:
every one of them produces Python that runs, and the worst of them
produce Python that runs and is quietly wrong.

The argument is one sentence. \textbf{A decorator runs; an attribute does
not}, and almost everything else in this chapter is that same distinction
in another costume \dash{} what has already happened by the time you are
holding the value, and what is still waiting to happen.

\section{A function is an object}
\label{sec:ch05-first-class}

You have this idea already, under two names. A delegate is a type; a
\code{Func<>} is a family of types indexed by arity; a method group
converts to one of them. Python has the idea without the ceremony: a
function is an ordinary value of an ordinary type, it may be stored,
passed, returned and put in a dictionary, and the annotation is the only
place a signature is written down.

\pyregion{code/ch05/first_class.py}{table}{A dispatch table: no delegate declaration, no arity in the type's name}{lst:ch05-table}

\begin{csbox}
The dictionary above is \code{Dictionary<string, Func<Job, bool>>}. Two
differences worth keeping. \code{Callable} takes its parameters as a list,
so arity is a shape rather than part of the name, and there is no separate
\code{Action}: a function returning nothing is one returning \code{None}.
And there is no \code{Invoke} and no method-group conversion, because there
was never a delegate type to convert to.
\end{csbox}

\noindent
That is the whole of the machinery. A decorator is a function applied to a
function; \code{functools.partial} is a function returning a function; a
key function is a function passed to another one. Nothing below introduces
a new kind of thing.

\section{A decorator runs; an attribute does not}
\label{sec:ch05-decorators}

This is the chapter's headline and the most expensive habit a .NET engineer
brings to Python. \code{[Timed]} in C\# is metadata. The compiler records
it, it changes nothing, and it does something only when a framework
reflects over it and decides to act. Reading \code{@timed} the same way is
reading it as inert, and it is not: \code{@timed} is a function call that
happens the instant the \code{def} statement finishes.

\pyregion{code/ch05/decorators.py}{definition_time}{The decorator runs at definition time; the body runs at call time}{lst:ch05-deftime}

\noindent
Run the file and the module has already recorded a line before anything is
called:

\transcript{ch05-decorators}

\mermaidfig{ch05-decorator-timeline}{A decorator is applied at definition time, and what it returns is what the name means afterwards}{when a decorator runs}

\begin{trapbox}
\textbf{A decorator is not metadata.} It is handed the function object and
whatever it returns replaces it, so a decorator may wrap it, log it, cache
it, register it somewhere, or return something that is not a function at
all. The closest C\# analogue is not an attribute; it is a piece of
middleware wrapped round the call, and \code{functools.wraps} is what stops
the wrapper's identity leaking into every log line and traceback
downstream. Without it, \code{parse.\_\_name\_\_} is \code{wrapper}.
\end{trapbox}

\noindent
A decorator that takes arguments is a function that returns a decorator,
which is three call levels and reads worse than it works.

\pyregion{code/ch05/decorators.py}{retry}{Three levels: the call, the decorator it returns, and the wrapper}{lst:ch05-retry}

\noindent
Measuring the call is the other half of what middleware does, and stacking
the two shows the order decorators apply in. They apply bottom-up, so
\code{@timed} written above \code{@retry} wraps the retrying wrapper and
therefore times all of the attempts rather than one of them.

\pyregion{code/ch05/decorators.py}{timing}{The other half of middleware, and why it prints no duration}{lst:ch05-timed}


The standard library ships several you will use rather than write.
\api{functools.lru\_cache} and \api{functools.cache} memoise on the
argument tuple, which means the arguments must be hashable and a
\code{list} argument raises \code{TypeError}; both hang a
\code{cache\_info()} onto the function, which is the sort of thing only a
decorator that \emph{replaces} the function could do.

\begin{note}
Agent middleware is the most visible use of this mechanism in the Python AI
stack, and it belongs to the companion volume: \emph{LangChain, LangGraph
and Async Python} spends a chapter on middleware ordering and the hooks
that compose it. This chapter owns the mechanism; that one owns the use.
\end{note}

\begin{exercise}{e05_01_audit}{A decorator that is middleware}
Write \code{audit} so it records every call and leaves the function
otherwise unchanged. Four assertions decide it: the return value, the
recorded calls, and \code{\_\_name\_\_} and \code{\_\_doc\_\_} surviving the
wrapping. The last two are the ones that fail if you forget
\api{functools.wraps}, and they are also the two nobody notices until a
traceback three services away says \code{wrapper}.
\end{exercise}

\section{Five kinds of parameter, and C\# has three}
\label{sec:ch05-parameters}

\code{*args} is \code{params}. Default values are optional arguments.
Passing by name is a named argument. Then Python has two markers with no
C\# spelling at all, and one collection with no C\# equivalent.

\pyregion{code/ch05/parameters.py}{signature}{Everything Python can say about a parameter, in one signature}{lst:ch05-signature}

\noindent
Everything before the \code{/} may only be passed positionally; everything
after the \code{*} may only be passed by name; and \code{**options}
collects names the function never declared. The \code{/} is worth more than
it looks. In C\# every parameter name is public surface forever, because
any caller may use it as a named argument and renaming it breaks them; the
marker is how Python takes that back.

\end{note}

\api{functools.partial} binds some arguments now and returns something
callable, which is as close as the standard library comes to a captured
delegate.

\section{A closure captures the variable, not its value}
\label{sec:ch05-closures}

If you wrote C\# before version~5 you have met this bug and you remember
the fix. A \code{foreach} body that captured the loop variable captured the
\emph{variable}, so every delegate saw the last value, and the cure was to
copy it into a fresh local inside the body. C\#~5 made \code{foreach} do
that for you. Python never did, and a comprehension is a loop.

\pyregion{code/ch05/late_binding.py}{trap}{Three closures over one variable}{lst:ch05-trap}

\transcript{ch05-late-binding}

\begin{trapbox}
\textbf{Every closure sees the last value.} The list holds three different
function objects and they share one cell, so the answer is
\code{[2, 2, 2]} rather than \code{[0, 1, 2]}. The two fixes are the same
fix: bind the value at the moment the function is made, either as a default
argument \dash{} evaluated once, at \code{def} \dash{} or by handing it to
\api{functools.partial}.
\end{trapbox}

\section{A comprehension is not a LINQ query}
\label{sec:ch05-comprehensions}

A comprehension reads like \code{Select} and \code{Where} with the clauses
reordered, and the reordering is not the difference that matters.

\begin{csbox}
\begin{csharp}
var worst = jobs
    .Where(j => j.Status == "failed")
    .OrderByDescending(j => j.Seconds)
    .Select(j => $"{j.Name} ({j.Seconds}s)")
    .Take(2);
\end{csharp}
Nothing has run. \code{worst} is an \code{IEnumerable<string>}, and
enumerating it twice runs the whole pipeline twice.
\end{csbox}

\pyregion{code/ch05/pipeline.py}{eager}{The same pipeline as a comprehension. It has run when it returns}{lst:ch05-eager}

\noindent
Swap the brackets for parentheses and it is deferred \dash{} and then it
differs from \code{IEnumerable} in the way that bites.

\pyregion{code/ch05/pipeline.py}{deferred}{Deferred, and exhausted by the first pass}{lst:ch05-deferred}

\transcript{ch05-pipeline}

\mermaidfig{ch05-eager-vs-lazy}{Three ways to spell one pipeline, and what each has done by the time it is handed back}{eager, deferred and re-runnable}

\begin{trapbox}
\textbf{A generator expression is single-pass.} A LINQ query is deferred
and re-runnable: walk it again and the pipeline runs again. A generator
expression is deferred and \emph{consumed} \dash{} the second pass is
empty, with no error and no warning. So a deferred pipeline is not a
drop-in for an \code{IEnumerable} you were going to hand to somebody else,
and the fix is to materialise it once, on purpose, with \code{list()}.
\end{trapbox}

\noindent
Note also what sorting did to the lazy version: it is not there. Ordering
cannot answer until it has seen every element, so a pipeline that orders
has run, whatever the rest of it promised. That is true of
\code{OrderBy} too; it is one of the few places the two languages agree
exactly. When a comprehension stops reading well, \pkg{itertools} is the
next thing to reach for: \api{islice} is \code{Take},
\api{takewhile} is \code{TakeWhile}, \api{chain} is \code{Concat}, and
\api{groupby} is \code{GroupBy} over \emph{sorted} input, which is the one
that surprises people.

\subsection{Building the string at the end}
\label{sec:ch05-join}

The C\# habit at the end of a pipeline is \code{+=} in a loop, and the
folklore says that is quadratic in Python. On the pinned interpreter the
folklore is wrong for the case people actually write, and right for a case
nobody expects. Ask the interpreter: disassemble a warmed-up loop and the
opcode is \code{\valtext{ch05.concat.opcode}}. When the left-hand string has no
other reference, it is resized in place and the loop is linear.

\code{code/measure/ch05\_concat.py} doubles the work and asserts the shape
rather than a duration, because a duration is a property of the machine.
Doubling the input multiplies linear work by two and quadratic work by
four, so the two bounds sit either side of that gap: the plain loop and
\code{"".join(...)} both come in under \val{ch05.concat.linear} going from
\val{ch05.concat.small} appends to \val{ch05.concat.large}, and the same
loop with one more reference to the string alive comes in over
\val{ch05.concat.quadratic} going from \val{ch05.concat.qsmall} to
\val{ch05.concat.qlarge}. The two pairs of sizes differ because they have
to, and that is the finding: the quadratic loop at the linear one's size
runs for minutes.

\begin{trapbox}
\textbf{It is fast until an unrelated line makes it slow.} Appending the
running string to a list, closing over it, or handing it to anything that
keeps it defeats the in-place resize, and the loop goes quadratic with
nothing at the call site changed. \code{"".join(pieces)} does not depend on
a reference count and does not have a bad case, which is why it is the
idiom even though \code{+=} is usually fine.
\end{trapbox}

\begin{exercise}{e05_03_pipeline}{The same query, eager and deferred}
Write the ordered, eager version and the deferred one. A module-level list
records every element the pipeline touches, and the tests read it to prove
which of the two has already run when it returns \dash{} so build both from
the source you are given rather than from a list you materialised first.
The last test walks the deferred one twice.
\end{exercise}

\section{A generator is an iterator block, and then some}
\label{sec:ch05-generators}

\code{yield} is \code{yield return}, and the mapping holds further than
most people expect: a generator is lazy, it is resumable, and a
\code{finally} inside it runs when the consumer stops early, which is what
\code{IEnumerator.Dispose} does at the end of a \code{foreach}.

\pyregion{code/ch05/generators.py}{yield_return}{An iterator block, including the cleanup on early exit}{lst:ch05-batched}

\noindent
Then it keeps going, into two things C\# has no spelling for.

\pyregion{code/ch05/generators.py}{two_way}{A value sent in, and a value returned out}{lst:ch05-twoway}

\transcript{ch05-generators}

\mermaidfig{ch05-generator-resume}{The three ways a suspended generator is resumed, and the one thing all three have in common}{resuming a generator}

\begin{trapbox}
\textbf{\code{yield} is an expression, not a statement.} It evaluates to
whatever the consumer sent in \dash{} \code{None} for a plain
\code{next()}, and the argument for \code{send()}. A generator that
\code{return}s carries the value out as well, which is why
\code{Generator} has three type parameters where \code{IEnumerable} has
one. That makes a Python generator a coroutine in the original sense, and
it is the machinery \code{async def} was built on top of. Chapter
\ref{ch:asyncio} is where coroutines proper are, and the first thing it
says about one is this same thing: it does nothing until something drives
it.
\end{trapbox}

\section{\code{with} is \code{using}, and contextlib is the rest}
\label{sec:ch05-with}

\code{using (var x = ...)} needs a type implementing \code{IDisposable},
which means writing a class. \code{with} needs a type with
\code{\_\_enter\_\_} and \code{\_\_exit\_\_} \dash{} and
\api{contextlib.contextmanager} builds one out of a generator, so the
common case is a function with a \code{yield} in the middle.

\pyregion{code/ch05/context.py}{contextmanager}{Everything before the yield is the enter; the finally is the exit}{lst:ch05-cm}

\begin{warning}
The \code{try}/\code{finally} is not decoration. Without it, an exception
raised in the body propagates out of the \code{yield} and the cleanup never
runs \dash{} which makes this the one thing here that is easier to get
wrong than a \code{using} statement, because a \code{using} cannot be
written without its release.
\end{warning}

\noindent
Two further differences earn their place, and both are in
\pkg{contextlib}:

\begin{itemize}[leftmargin=1.4em, itemsep=2pt]
  \item \api{suppress} \dash{} \code{\_\_exit\_\_} is handed the exception
        and may swallow it, which \code{Dispose} cannot.
  \item \api{ExitStack} \dash{} it holds a number of contexts not known
        until run time, and unwinds them in reverse, which nested
        \code{using} statements cannot express.
\end{itemize}

\pyregion{code/ch05/context.py}{exitstack}{A number of contexts decided at run time}{lst:ch05-exitstack}

\begin{versionbox}
Write the return type as \code{Generator[str]}, not the
\code{Iterator[str]} every tutorial shows. The stubs \pkg{pyright}
\pyrightver{} ships mark that overload deprecated, in as many words:
\enquote{annotating the return type as \code{-> Iterator[Foo]} with
\code{@contextmanager} is deprecated. Use \code{-> Generator[Foo]}
instead.} The code runs either way; the checker is what changed.
\end{versionbox}

\begin{exercise}{e05_04_lease}{A context manager that always releases}
Write \code{lease} with \api{contextlib.contextmanager}. The test that
matters is the one that raises inside the body: a generator-based context
manager without a \code{try}/\code{finally} looks correct until something
throws. A fourth test nests two of them and checks they unwind in reverse.
\end{exercise}

\section{\code{match}, and the pattern that is not a comparison}
\label{sec:ch05-match}

A modern C\# switch expression already gives you type, property and
relational patterns. \code{match} has those, plus sequence and mapping
patterns, and one rule with no C\# counterpart.

\pyregion{code/ch05/matching.py}{match}{Type, property, guard, sequence, mapping and value patterns}{lst:ch05-match}

\transcript{ch05-matching}

\noindent
Note the declared union above the function. An \code{object} parameter
makes every capture untyped; a union is what a switch over a sealed
hierarchy has, and it is what lets the checker narrow inside each case.

\begin{trapbox}
\textbf{A bare name in a pattern captures; it does not compare.}
\code{case ACTIVE:} does not test the value against the constant
\code{ACTIVE}. It matches anything at all and rebinds the name locally. The
spelling that compares is the dotted one, \code{case Status.ACTIVE:}, and
the rule has one piece of good news attached: Python refuses to compile a
bare capture when a case follows it, saying the remaining patterns are
unreachable. It compiles in silence only when it is the last case \dash{}
which is exactly where it survives review.
\end{trapbox}

\pyregion{code/ch05/matching.py}{capture}{The one place the capture rule compiles quietly}{lst:ch05-capture}

\section{What this bought you}
\label{sec:ch05-summary}

\begin{center}
\small
\begin{tabularx}{\linewidth}{@{}lX@{}}
\toprule
\textbf{C\#} & \textbf{Python} \\
\midrule
\code{Func<>}, delegate & a function, annotated \code{Callable[[A], B]} \\
an attribute a framework reads & nothing; a decorator \emph{runs} \\
middleware round a call & a decorator \\
\code{params}, optional, named & \code{*args}, defaults, keywords \\
--- & \code{/} and \code{*} markers, \code{**kwargs} \\
LINQ, deferred and re-runnable & a comprehension, eager; or a generator
  expression, deferred and single-pass \\
\code{yield return} & \code{yield}, plus \code{send} and a return value \\
\code{using} / \code{IDisposable} & \code{with} / \api{contextmanager} \\
switch expression & \code{match}, with sequence and mapping patterns \\
\bottomrule
\end{tabularx}
\end{center}

\noindent
The payoff is the one the chapter opened with. Everything above turns on
when a thing runs: at definition or at call, at the bracket or at the walk,
once or on every pass. A C\# engineer reading Python fast will assume
\emph{later} and be wrong about comprehensions, and assume \emph{never} and
be wrong about decorators. Ask of every construct in this chapter: has this
already happened? The answer is the whole of the difference.
