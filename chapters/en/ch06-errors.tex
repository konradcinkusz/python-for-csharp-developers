\chapter{Errors: exceptions as control flow, EAFP, ExceptionGroup and the Result pattern}
\label{ch:errors}

\noindent
A C\# method that can fail usually says so in its shape. \code{TryParse}
returns a \code{bool} and hands the answer back through an \code{out}
parameter; \code{FirstOrDefault} hands back a default rather than throwing; a
nullable reference type is annotated and the compiler nags. Throwing is for the exceptional
case, and the word is in the name of the base class.

Python's base class is called \code{Exception} too, and almost none of the
rest of it carries over. Here a dictionary lookup that misses raises, a
\code{for} loop ends by raising, and reading an absent attribute raises.
None of those three is a fault. Code that treats them as faults is handling
normal operation, and the handler that does it is usually the one that hides
the real failure later.

Underneath the difference in style there is a difference in cost, and it is
measurable rather than a matter of taste. That is where this chapter starts,
because once the cost is on the table the rest of the chapter's advice stops
being advice and becomes arithmetic.

\begin{note}
Cancellation and timeouts are not here. \code{CancelledError} is an ordinary
exception delivered through the ordinary mechanism, but everything about
\emph{when} it arrives is a property of the event loop, and that belongs to
Chapter~\ref{ch:asyncio} and to the companion volume on asynchronous Python.
\end{note}

\section{What a try costs, and what a check costs}
\label{sec:ch06-cost}
\index{EAFP}
\index{LBYL}

Two ways to read a value that might not be there. Look before you leap: ask,
then act.

\pyregion{code/ch06/eafp_lbyl.py}{lbyl}{Ask first, then act}{lst:ch06-lbyl}

\noindent
Or easier to ask forgiveness than permission: act, and handle the one
failure you expect.

\pyregion{code/ch06/eafp_lbyl.py}{eafp}{Act, and handle the one failure}{lst:ch06-eafp}

\noindent
Both return the same answers. They do not cost the same, and the difference
is not where a C\# habit expects it. Experiment~E3 counts the bytecode
instructions each shape actually executes, which is exact and comes out the
same on any machine running this interpreter, because CPython's compiler
does not depend on the hardware.

\begin{center}
\small
\begin{tabularx}{\linewidth}{@{}Xrr@{}}
\toprule
& \textbf{key present} & \textbf{key absent} \\
\midrule
\code{rates[code]}, no guard at all & \val{e03.plain.happy} & \val{e03.plain.unhappy} \\
Ask first (\code{if code in rates}) & \val{e03.lbyl.happy} & \val{e03.lbyl.unhappy} \\
Act and handle (\code{try} / \code{except}) & \val{e03.eafp.happy} & \val{e03.eafp.unhappy} \\
\bottomrule
\end{tabularx}
\end{center}

\noindent
Read the first row as the floor: that is what the work itself costs. Wrapping
it in a \code{try} adds \val{e03.try.overhead} instruction. Asking first adds
\val{e03.lbyl.happy}~$-$~\val{e03.plain.happy}, on every call, whether the key
is there or not. The handler does not sit on the path at all: it compiles into
an exception table of \val{e03.exctable}~bytes beside the code, which is what
\emph{zero-cost exceptions} means and why the \code{try} is the cheaper of the
two when nothing goes wrong.

When something does go wrong the order reverses, and by more than the
instruction counts suggest, because raising also builds an exception object
and a traceback. Timed on the machine that built this page, raising and
catching cost several times what the same function costs when it returns
normally. On every build the script asserts that raising stays above
\val{e03.raise.floor} times a normal return and that a \code{try} which does
not fire stays under \val{e03.try.ceiling} times the check, and it prints its
own machine's nanoseconds, which are not committed here because a nanosecond
is a property of a machine.

\begin{csbox}
\code{TryGetValue} is the LBYL shape with the second lookup removed, and it
is the reason the C\# instinct is sound in C\#: there, asking is cheap and
throwing is expensive enough that guarding is nearly always right. In Python
the guard costs more than the \code{try} and the \code{try} costs more only
when it fires, so the crossover sits much further towards exceptions than
the instinct allows.
\end{csbox}

\noindent
Cost is not the whole argument, and the second half is the one that survives
a faster interpreter. A check is a question asked at one moment about a state
that can change at the next.

\pyregion{code/ch06/eafp_lbyl.py}{race}{A mapping that changes between the question and the act}{lst:ch06-race}

\noindent
\code{lookup\_lbyl} raises \code{KeyError} on that mapping. \code{lookup\_eafp}
returns the value, because it never asked a question whose answer could go
stale. A hostile \code{dict} subclass is a caricature; a cache with an
eviction thread, a file another process can unlink and a row another
transaction can delete are not.

So the rule is about the failure rate and about recovery, not about taste:
act and handle where failure is rare and you can answer it, ask where failure
is routine, and where you cannot recover, do neither and let it out.

\mermaidfig{err-cost}{The two shapes, and the question that chooses between them}{EAFP against LBYL, and what each costs}

\begin{exercise}{e06_01_field}{Ask forgiveness, and say who is asking}
Write \code{field\_of} in the EAFP shape: read the named field, and turn the
one failure you expect into this module's own error with the original
attached. The test checks \code{\_\_cause\_\_}, so \code{raise~...~from} is
not decoration here \dash{} Section~\ref{sec:ch06-keywords} says what it is
for.
\end{exercise}

\section{Three exceptions that are not failures}
\label{sec:ch06-protocol}
\index{exceptions!as protocol}

\code{KeyError}, \code{StopIteration} and \code{AttributeError} are not
error conditions. They are how three of Python's protocols say \emph{no},
and each one is normally raised, caught and discarded one level up without
anybody's code seeing it.

The clearest is the loop. A \code{for} statement does not test a
has-more-items flag, because there is not one. It calls \code{next} until
\code{next} raises.

\pyregion{code/ch06/protocol.py}{forloop}{What a for loop compiles to}{lst:ch06-forloop}

\noindent
\code{dict.get} is the same shape with the same relationship to
\code{KeyError}, and \code{hasattr} is the same shape again around
\code{AttributeError} \dash{} it does the access, catches, and throws the
answer away.

\pyregion{code/ch06/protocol.py}{getattr}{hasattr, written out}{lst:ch06-getattr}

\begin{trapbox}
\textbf{\enquote{A \code{KeyError} in the log means something went wrong.}}
It means a lookup missed, which may be the most ordinary thing in the
program. What is worth alarming on is a \code{KeyError} that escaped the
function that should have answered it \dash{} which is a different query,
and one you can only write once you have stopped treating the class as a
fault.
\end{trapbox}

\noindent
There is a second habit in the same family, and it is about the absence of a
value rather than the absence of a key. C\# has one falsehood and it is
\code{false}. Python has several: an empty list, an empty string, zero and
\code{None} are all false in a condition.

\pyregion{code/ch06/protocol.py}{truthiness}{Two questions a C\# habit runs together}{lst:ch06-truthiness}

\noindent
\code{if rows:} asks whether there is anything to do. \code{if rows is not
None:} asks whether the caller passed a list at all. An empty list answers
the first with no and the second with yes, and the two questions are
confused most often in exactly the place it matters: the guard at the top of
a function that is about to decide whether its input is missing or merely
empty.

\section{What a function raises, and who tells you}
\label{sec:ch06-contract}
\index{exceptions!documenting}

Nothing in the type system carries exceptions. A signature ending
\code{-> int} tells you nothing about what the function does instead of
returning one, pyright will not tell you either, and Python has no
equivalent of Java's checked exceptions for it to check. What stands in
their place is a docstring, and a docstring is prose: nothing verifies it,
so it is exactly as true as the last person to edit the function left it.

\pyregion{code/ch06/boundary.py}{translate}{The contract, in the only place Python has to put it}{lst:ch06-translate}

\noindent
That makes the \emph{shape} of what you raise carry more weight than it does
in C\#, because the shape is the part a caller can discover without reading
you. Give a module one base class and derive the rest from it, so that a
caller who wants everything can catch one name and a caller who wants one
thing can catch that.

\pyregion{code/ch06/boundary.py}{hierarchy}{One base class, and the reason for it}{lst:ch06-hierarchy}

\begin{csbox}
C\# has no checked exceptions either, so this is not the gap it looks like
\dash{} the habit that transfers badly is the tooling around it. There, an
\code{<exception cref="..."/>} tag surfaces in the editor and
\code{ArgumentNullException} is a convention the framework shares with you.
Here the base class is the convention, and the naming one goes the other way:
Python's suffix is \code{Error}, not \code{Exception}, and the linter this
book pins enforces it \dash{} a class called \code{JobUnavailable} is
reported until it is called \code{JobUnavailableError}.
\end{csbox}

\section{Four keywords, and three ways to lose a failure}
\label{sec:ch06-keywords}
\index{exceptions!chaining}

\code{try} and \code{except} do what \code{try} and \code{catch} do.
\code{finally} does what \code{finally} does. The fourth keyword has no C\#
equivalent: \code{else} runs when the \code{try} block did \emph{not} raise,
before \code{finally}, and it exists so that the body of the \code{try} can
be narrowed to the one statement whose failure you meant to catch. Code that
belongs after the risky call goes in the \code{else}, where it is not itself
protected by a handler written for something else.

The interesting part is what happens when a handler re-raises. A C\# stack
trace is attached at the throw site, so \code{throw ex;} truncates it and
\code{throw;} does not, and every C\# engineer has learned that difference
the hard way. Python attaches the traceback to the exception \emph{object},
and the consequence is not the one the habit predicts.

\pyregion{code/ch06/chaining.py}{shapes}{Four ways to re-raise}{lst:ch06-shapes}

\noindent
Running that prints the frames each exception carries and what it says about
the exception it came from:

\transcript{ch06-chaining}

\begin{trapbox}
\textbf{\enquote{\code{raise exc} loses the traceback, like \code{throw ex;}.}}
It does not. The traceback lives on the exception object, so re-raising the
same object keeps every frame under it and \emph{adds} the re-raise line
\dash{} which is why \code{raise\_exc} above shows its own frame twice. Bare
\code{raise} is still the better habit, because the duplicate frame is
noise, but nothing is lost and no stack is truncated. The C\# rule does not
transfer, and neither does the anxiety.
\end{trapbox}

\noindent
What you can lose is the \emph{link}. \code{wrap\_from} sets
\code{\_\_cause\_\_} and the printed failure says the first exception was
the direct cause of the second. \code{wrap\_plain} sets only
\code{\_\_context\_\_}, and the printed failure says another exception
occurred while the first was being handled \dash{} which reads like an
accident in your error handler rather than a deliberate translation. The
difference is three characters, and the linter asks for them.

\mermaidfig{err-chaining}{What each re-raise leaves for whoever reads the failure}{raise from against a plain raise}

\noindent
Three shapes lose a failure outright. The first two are C\# reflexes.

\pyregion{code/ch06/swallow.py}{blind}{A crash becomes a number}{lst:ch06-blind}

\begin{trapbox}
\textbf{\enquote{Catch \code{Exception}, log it, carry on \dash{} defensive.}}
It converts a crash into a wrong answer. The ledger above is half-written
when the handler runs, and the function returns a total anyway; nothing
downstream can tell it apart from a correct one. And a bare \code{except:}
is worse again, because it catches \code{KeyboardInterrupt} and
\code{SystemExit} as well \dash{} both are \code{BaseException} and neither
is an \code{Exception} \dash{} so the process stops being stoppable.
\end{trapbox}

\noindent
The third is \code{return} inside \code{finally}, which discards any
exception in flight and returns as if nothing had happened. On this
interpreter the compiler now says so. It still does it.

\transcript{ch06-swallow}

\noindent
That transcript is the chapter in four lines. Two of the three shapes are
caught by the tooling this book pins \dash{} the bare \code{except} and the
\code{return} in \code{finally} are both reported by ruff, and the compiler
names the second one itself. Catching \code{Exception} and carrying on is
reported by nothing at all, which is why it is the one that reaches
production. The fix is the same in every case: catch the failure you can
answer, answer it, and let the rest out.

\pyregion{code/ch06/swallow.py}{narrow}{The same loop, answering the one failure it can}{lst:ch06-narrow}

\noindent
Where you genuinely want a failure ignored, say so in one line.

\noindent
\code{contextlib.suppress} is a context manager wrapping exactly the
\code{try} / \code{except} / \code{pass} you would otherwise write. Its
virtue is that it names the exception it is discarding, and so cannot
accidentally discard a second one.

\begin{exercise}{e06_02_cleanup}{Close it on both paths, and let the failure out}
\code{read\_all} must return every row and close the cursor whether or not
the read raised, without turning the failure into a value. \code{using} does
both halves for you in C\#; here you write one of them, and the obvious
first draft passes the happy-path test while leaking the handle on every
other path.
\end{exercise}

\begin{exercise}{e06_04_swallowed}{Stop swallowing}
\code{total} sums rows that arrived as text. The draft it replaces wrapped
the whole sum in \code{except Exception} and answered zero, so a bad batch
was indistinguishable from an empty one and no tool in this book's chain
said a word. Write the version that raises instead, naming the offending
row, with the original as its cause.
\end{exercise}

\section{More than one failure at a time}
\label{sec:ch06-groups}
\index{ExceptionGroup@\texttt{ExceptionGroup}}

A handler catches one exception. That is a problem whenever the work was
plural: validate a record against several rules and stop at the first, and
the caller fixes it, runs the job again and meets the second.

\pyregion{code/ch06/groups.py}{collect}{Run every check, then raise once}{lst:ch06-collect}

\noindent
\code{ExceptionGroup} is the container, and \code{except*} is what makes it
more than a list. Every clause that matches something in the group runs
\dash{} not the first matching clause, every one of them \dash{} and
whatever no clause matched keeps propagating, still a group.

\pyregion{code/ch06/groups.py}{handle}{Handle what this layer can answer}{lst:ch06-handle}

\transcript{ch06-groups}

\begin{csbox}
\code{AggregateException} is a container you catch as a single exception and
then take apart yourself, usually with a loop over
\code{InnerExceptions} and a re-throw of what you could not handle. An
\code{ExceptionGroup} is taken apart by the language, and the part you did
not handle re-raises itself. The nearest C\# construct to \code{except*} is
a \code{catch} with a \code{when} filter over \code{InnerExceptions}, except
that only one \code{catch} block can ever run.
\end{csbox}

\mermaidfig{err-group}{One raise, several handlers, and a remainder that carries on}{ExceptionGroup and except*}

\begin{exercise}{e06_03_group}{Report every failure, not the first}
Write \code{check\_all} so that it runs every check over a record and raises
once, carrying all of the failures, in order \dash{} and raises nothing at
all when every check passes.
\end{exercise}

\section{At the boundary}
\label{sec:ch06-boundary}
\index{exceptions!at a boundary}

The two libraries a service in this book leans on both fail through
exceptions, and both are worth a sentence because their hierarchies are the
thing you catch on. \pkg{pydantic}'s \code{ValidationError} is a subclass of
\code{ValueError}, so a handler written for bad input catches it without
knowing the library exists, and it carries a list of errors rather than the
first one. \pkg{httpx} puts \code{HTTPStatusError} and every transport
failure under one \code{HTTPError}, so a single \code{except} covers both a
bad status and a connection that never opened.

\code{parse\_job} in Listing~\ref{lst:ch06-translate} is the whole pattern:
catch the library's exception at the edge of your module, raise your own
with \code{from}, and let the caller depend on your hierarchy rather than on
\pkg{httpx}'s. The import stops at the boundary along with the exception.

That leaves the pattern a C\# engineer with a functional streak reaches for
here, and the honest answer is that it earns its place in one position and
not the other. A \code{Result} or \code{Either} type inside a call chain
costs a branch at every call site and discards the traceback that would have
named the line; the language already has a mechanism for \emph{this went
wrong and I cannot continue}, and it is better at it. But where the caller
genuinely wants one answer per item rather than the first failure, a
Result-shaped return is right \dash{} and in Python it needs no Result type.

\pyregion{code/ch06/boundary.py}{batch}{The shape a Result type is reaching for}{lst:ch06-batch}

\noindent
Two lists, or a group raised once. Both say the same thing: when failure is
plural, return or raise all of it.

\begin{warning}
The parsing above runs against a response built in the test, not against a
live service, which is why it is in the book at all: \code{raise\_for\_status}
is a pure function of the status line, so a listing that exercises it needs
no network and neither does your test suite.
\end{warning}

\noindent
Which returns the chapter to the sentence it opened with. Python raises where
C\# checks, and the reason is not that Python is careless about failure. It
is that the guard costs more than the attempt, the attempt costs nothing
until it fails, and the failure carries more information than a
\code{false} ever did. What the language asks of you in exchange is the part
no tool can check: catch what you can answer, name what you raise, and leave
the rest alone.
