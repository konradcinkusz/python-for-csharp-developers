\chapter{Data: SQLAlchemy 2.0 for people who know EF Core, and polars for the LINQ reflex}
\label{ch:data}
\index{SQLAlchemy}

\noindent
A SQLAlchemy \code{Session} is a unit of work in the sense a \code{DbContext}
is one: it tracks the objects you put in it, works out what changed, and
writes the lot in one transaction. Almost everything you know transfers. What
does not transfer is a short list, every item on it produces code that runs
and is wrong, and the ones that cost the most are measured here rather than
asserted \dash{} which is what the rest of this chapter is for.

The model in every listing here is two tables \dash{} a service, and the
incidents raised against it, \val{e06.services} rows of the first and
\val{e06.incidents} of the second \dash{} and it lives in one file the other
listings import, so nothing below is about a different schema from anything
else. The database is SQLite, in memory, seeded on every run: the whole
chapter is free to re-run and needs no server.

\section{The \code{Session} is a \code{DbContext}}
\label{sec:ch10-session}
\index{Session@\texttt{Session}}

Declarative mapping is the entity class with the fluent configuration moved
onto the attribute. \code{Mapped[str]} is the column's type \emph{and} its
NOT NULL; \code{Mapped[str | None]} is the nullable one.
\code{mapped\_column()} is where a key, a default, a unique constraint or an
index goes, and there is no \code{OnModelCreating} anywhere.

\pyregion{code/ch10/model.py}{model}{The model both tables and every later listing share}{lst:ch10-model}

\begin{csbox}
\code{DbSet<Service> Services} has no counterpart and needs none: a query
names the entity class, not a property of a context. One
\code{DeclarativeBase} subclass is one \code{DbContext} \dash{} it owns the
metadata, which is what \code{Database.EnsureCreated()} and every migration
act on. \code{back\_populates} is the two halves of a navigation property
told about each other, which EF infers from the types and SQLAlchemy asks
you to say.
\end{csbox}

A query is composed and then executed, exactly as LINQ to Entities is:
\code{select()} builds an object, \code{.where()} and \code{.join()} and
\code{.order\_by()} return new ones, and nothing reaches the database until
the statement is handed to the session.

\pyregion{code/ch10/session.py}{query}{\code{select()} composes; \code{scalars()} executes}{lst:ch10-query}

The difference from LINQ is that there is one API and not two. There is no
\code{IEnumerable} twin with the same shape, so the LINQ hazard \dash{} a
mistyped variable quietly moving the whole query in process \dash{} has
nothing to happen to. A clause that cannot become SQL fails where you wrote
it rather than succeeding somewhere slower; what it fails with is another
matter, and is often an ordinary \code{TypeError} rather than anything
about translation.

Two moments inside the session are worth naming, because EF habits attach
to both. The identity map means two loads of one row give you one object,
and the second costs nothing \dash{} the same guarantee change tracking
gives you, and the listing counts the second rather than asserting it.

\pyregion{code/ch10/session.py}{identity}{Two loads, one object, no second statement}{lst:ch10-identity}

And \code{flush()} is not \code{commit()}: the flush runs the INSERT and
hands back the key the database chose, while the transaction is still open
and can still be rolled back.

\pyregion{code/ch10/session.py}{flush}{\code{flush()} writes; \code{commit()} ends the transaction}{lst:ch10-flush}

\mermaidfig{orm-unit-of-work}{The three moments in a unit of work, and what each one costs}{the Session's three moments}

\section{The query you did not write}
\label{sec:ch10-expire}
\index{expire\_on\_commit@\texttt{expire\_on\_commit}}

Here is a function you have written in C\# a hundred times. It loads every
service, renames each one, commits, and returns the new names. The rename is
a plain attribute assignment; the read at the end is a plain attribute
access. Before you read on: how many statements does it send?

\pyregion{code/ch10/expiry.py}{expired}{Rename, commit, then read the names back}{lst:ch10-expiry}

\transcript{ch10-expiry}

\noindent
\val{e06.expire.selects} SELECTs, for \val{e06.services} objects you already
had, from a line with no query in it, against \val{e06.expire.kept} when the
flag is turned off. The count is not a coincidence and it is not a constant:
it is one per object.

\begin{trapbox}
\textbf{\enquote{A \code{Session} is a \code{DbContext}, so after
\code{commit()} my objects are still usable.}} They are usable and they are
empty. \code{expire\_on\_commit} defaults to \code{True}, so a commit marks
every attribute of every tracked object as stale, and the next access
reloads it \dash{} one statement per object, issued by a line that reads
like a field access. EF Core does not do this, which is why the habit has
nothing to warn you.

The fix is one argument, and the other fix is better: read what you need
into plain values \emph{before} you commit, and stop holding the objects at
all.
\end{trapbox}

\section{The N+1, counted}
\label{sec:ch10-nplusone}
\index{N+1@N\texttt{+}1 problem}

A relationship is lazy by default, exactly as a navigation property is, so
the loop everybody writes has the same shape in both languages. Before
counting it, here is the instrument, because a measurement is worth what its
instrument is worth.

\pyregion{code/ch10/counting.py}{counter}{The instrument: every statement counted twice, from both ends}{lst:ch10-counting}

\noindent
The engine's echo prints every statement it runs, and the event the echo is
emitted from can be hooked. Counting both and refusing to report a number
the two disagree about is three extra lines, and it is the difference
between a count and a claim. Note the log level is raised and restored
rather than assumed: an echo-counting instrument pointed at an engine whose
logger sits at WARNING counts nothing, agrees with nothing, and reports a
confident zero.

Now the loop. It sums each service's lost minutes, and there are
\val{e06.services} services.

\pyregion{code/ch10/nplusone.py}{lazy}{The obvious loop}{lst:ch10-lazy}

\pyregion{code/ch10/nplusone.py}{eager}{\code{selectinload} is \code{Include}; \code{joinedload} is \code{Include} with a join}{lst:ch10-eager}

\transcript{ch10-nplusone}

\noindent
So the loop costs \val{e06.lazy.selects}, the eager loader costs
\val{e06.selectin.selects} and the join costs
\val{e06.joined.selects}. Three numbers on one database prove nothing about
a bigger one, so the experiment sweeps the parent count and asserts the
shape rather than the figures:

\noindent
The left column grows with the table and the right column does not, which is
the only version of this claim that survives a production database.

\mermaidfig{orm-n-plus-one}{What the loop costs, and what saying so up front costs instead}{the N+1 and its fix}

\begin{trapbox}
\textbf{\enquote{Relationships are loaded when I read them, as in EF.}} They
are, and that is the problem rather than the reassurance. The N+1 is
identical in both, \code{selectinload} is \code{Include}, and the one real
difference is that SQLAlchemy will also let you turn the silent version into
a loud one.
\end{trapbox}

\code{raiseload} is the part with no convenient EF counterpart. It refuses
to lazy-load rather than doing it, so an N+1 becomes a failing test rather
than a slow endpoint.

\pyregion{code/ch10/nplusone.py}{raiseload}{Make the silent version loud}{lst:ch10-raiseload}

\begin{note}
\code{joinedload} costs one statement rather than two and is not therefore
the better answer. It repeats every parent row once per child, which is why
its result needs \code{.unique()}; on a parent with wide columns and many
children that is a great deal of duplicated bytes over the wire.
\code{selectinload} is the sensible default and \code{joinedload} is for a
to-one relationship.
\end{note}

\section{Async, where the N+1 is loud}
\label{sec:ch10-async}
\index{AsyncSession@\texttt{AsyncSession}}

Chapter~\ref{ch:services} serves everything asynchronously, so the session
under it is \code{AsyncSession}. Almost all of this chapter transfers with
an \code{await} in front of the calls that touch the database. One thing
does not, and it is the one the previous section was about.

\pyregion{code/ch10/async_session.py}{lazy}{The same loop, asynchronously}{lst:ch10-async}

\transcript{ch10-async}

\noindent
Under the async session a lazy relationship does not quietly issue a query.
\code{MissingGreenlet} is what it raises instead, because issuing one there
would mean blocking the event loop, and the thing Chapter~\ref{ch:asyncio}
is about is that nothing may. Half of the previous section survives the
move: lazy is still the default, and the async session declines to act on
it.

That is worth stating as a rule rather than an anecdote, because it runs the
opposite way to the usual advice. \textbf{The N+1 is silent in a synchronous
service and loud in an asynchronous one.} A team porting a sync service to
async does not acquire the bug; it acquires the error message for the bug it
already had.

\begin{csbox}
The same argument explains why \code{expire\_on\_commit=False} is not a
tuning knob under async. An expired attribute reloads itself on access, and
that reload is the error above rather than a query, so leaving the default
on arms a landmine at every commit. Async EF has no equivalent hazard,
because change tracking never issues a query behind your back.
\end{csbox}

\section{Autogenerate is a diff, not a truth}
\label{sec:ch10-alembic}
\index{Alembic}

Alembic is the migration tool, and \code{alembic revision --autogenerate} is
two steps: diff the models against the live database, then write the diff
out as a migration script. It is worth watching the first step on its own.
Here are two versions of one model, differing by a single renamed column,
and then the function the command itself calls.

\pyregion{code/ch10/autogenerate.py}{models}{What shipped, and what the models say now}{lst:ch10-models}

\pyregion{code/ch10/autogenerate.py}{diff}{What \code{-{}-autogenerate} computes}{lst:ch10-autogen}

\transcript{ch10-autogenerate}

\begin{trapbox}
\textbf{\enquote{Alembic autogenerate is the migration.}} It is a diff, and
a diff cannot see a rename: it sees a column that is gone and a column that
is new, and nothing in the models says they are the same column. Applied as
generated, that migration drops the data and creates an empty column beside
it.

EF Core's \code{Add-Migration} has the same blind spot and hides it less
well, because the model snapshot at least gives it something to compare
against. Read every generated migration. The generated file is a draft.
\end{trapbox}

The rest of the workflow maps cleanly, and the last row is the one worth
knowing: revisions form a chain by parent id rather than an ordering by
timestamp, which is what makes two branches merge-conflict rather than
silently interleave.

\section{A data layer with no repository}
\label{sec:ch10-no-repository}

The pattern a .NET team reaches for next is a repository over the ORM, and
it is usually a mistake here for a reason that is not about taste. The
\code{Session} \emph{is} the unit of work and the repository; wrapping it
gives you a second one, with its own lifetime to get wrong, and the first
thing the wrapper has to leak is the transaction, because a transaction
spans several repositories by definition.

What replaces it is a module of functions whose first parameter is the
session.

\pyregion{code/ch10/queries.py}{queries}{Queries are functions; the session is the parameter}{lst:ch10-queries}

\noindent
The caller owns the transaction, which is what lets a batch be one unit of
work rather than several.

\pyregion{code/ch10/queries.py}{caller}{\code{session.begin()} is the transaction scope}{lst:ch10-begin}

\begin{trapbox}
\textbf{\enquote{I need a repository over the ORM.}} The two arguments
usually given for one are testability and swappability. Testability is
answered by the session: Chapter~\ref{ch:testing} builds these tests against
SQLite in memory, and they are faster than a mock and check the SQL as well.
Swappability is answered by asking when you last swapped one. What a
repository does reliably deliver is a second place for the N+1 to hide,
because a method that returns an entity cannot know whether its caller is
about to walk a relationship.
\end{trapbox}

\begin{note}
SQLite in memory is the right test database for the shape of this code and
the wrong one for anything the two engines disagree about \dash{} and they
disagree about a great deal: type affinity, the exact constraint violations,
and what a concurrent write does. Run the test suite against SQLite for
speed and the same suite against the real engine before a release.
\end{note}

\section{polars, and the LINQ reflex}
\label{sec:ch10-polars}
\index{polars}

The other habit worth mapping is LINQ over a table that is not in a
database. \pkg{polars} has two types where LINQ has two interfaces, and the
correspondence is close enough to be useful: a \code{DataFrame} is an
\code{IEnumerable} that has already been materialised, and a
\code{LazyFrame} is an \code{IQueryable}.

\pyregion{code/ch10/frames.py}{lazy}{Nothing here reads a row}{lst:ch10-lazyframe}

\pyregion{code/ch10/frames.py}{collect}{\code{collect()} is \code{ToList()}}{lst:ch10-collect}

\transcript{ch10-frames}

\noindent
\code{pl.col("severity") <= 2} is an object describing a comparison, not a
lambda over a row. That is an expression tree by another name, and it is
there for the reason \code{Expression<Func<T, bool>>} is: something other
than the host language has to read it. The payoff is the same too \dash{}
the plan the listing prints carries the filter down into the file scan, so
rows that fail it are never decoded.

\mermaidfig{polars-lazy-plan}{Build a plan, let it be rewritten, run it once}{polars' two types}

\begin{note}
\pkg{pandas} is the one everybody has heard of, and for this reader it is
rarely the right answer: its index is a concept with no LINQ counterpart and
a great deal of surprising behaviour, and almost every tutorial written for
it predates the parts that are now reasonable. Reach for \pkg{pandas} when a
library you must use returns or demands a \pkg{pandas} frame, which does
happen in the AI toolchain and is Chapter~\ref{ch:aitoolkit}'s problem.
\end{note}

\begin{note}
\pkg{polars} does not type-check strictly at the version this book pins: its
frame methods carry unions wide enough that a strict checker calls the
chained result partially unknown. The checker is right and the stubs are the
reason, so the two listings above carry a named suppression rather than the
project relaxing its strict mode. That is the shape
Chapter~\ref{ch:typing} recommends \dash{} suppress the rule you mean, at
the place you mean it.
\end{note}

\section*{Exercises}

Five, and every one is a starter file with a test beside it. Three of them
check what your answer \emph{cost} as well as what it said, because that is
the half of this chapter a passing test would otherwise miss.

\begin{exercise}{e10_01_select}{Compose the query}
Return the names of every service with at least one severity-1 incident, in
alphabetical order. The test checks the answer and the cost: loading every
service and filtering in a loop gives the same list and six statements.
\end{exercise}

\begin{exercise}{e10_02_expire}{Read your own objects back}
Upper-case every service name, commit, and return the names in id order, in
one statement rather than one per row. There are two good answers and the
solution's docstring says which is better when the session is long-lived.
\end{exercise}

\begin{exercise}{e10_03_eager}{Right answer, wrong number of queries}
This starter already returns the right answer. Its test fails on what the
answer cost. Fix that without changing what it returns.
\end{exercise}

\begin{exercise}{e10_04_unit_of_work}{All of them, or none of them}
Record several incidents in one batch. An entry naming a service that does
not exist must take the whole batch with it, leaving the database as it was.
The two good rows will already have been written by the time the bad one is
found, so the transaction has to take them back out.
\end{exercise}

\begin{exercise}{e10_05_polars}{Return the plan, not the rows}
Write the lazy query for minutes lost per service, heaviest first. The test
checks the rows and that what you returned is still a \code{LazyFrame}: a
function ending in \code{.collect()} has done the work before its caller
asked for it.
\end{exercise}
