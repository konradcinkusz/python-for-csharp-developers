\chapter{Environments and packaging: uv, pyproject and the lockfile}
\label{ch:packaging}

\noindent
In .NET the environment is a property of the machine and you have never had
to think about it. The SDK is installed once, \code{dotnet restore} fills one
package cache that every project on the box reads from, and the version of
the runtime a project wants is a line in a file that the tooling honours
without being asked. It works so reliably that it is invisible.

Python inverts that, and the inversion is the whole chapter.
\textbf{A Python environment is a directory.} It is not a registry key, not a
machine-wide install and not a setting some tool reads; it is a folder with an
interpreter in it, and the only thing that makes it \emph{your} environment is
that a command you ran happened to point at it. Nothing in the language
enforces the arrangement, nothing warns you when you are outside it, and every
way this goes wrong for a .NET engineer follows from that one fact.

\bottomrule
\end{tabularx}

\noindent
One row of that table is a genuine gap rather than a translation.
\pkg{pre-commit} runs your formatter and your linter as a git hook, on the
files a commit touches, before the commit is made. .NET has no equivalent in
common use, because analysers run in the build and the build runs constantly.
Python's build does not run constantly \dash{} there is no build \dash{} so the
hook is where the equivalent pressure has to come from.

\section{An environment is a directory}
\label{sec:ch02-directory}
\index{environment!virtual}
\index{packaging!uv}

\noindent
Before you read on, answer this from your current model of Python. You type
\code{pip install httpx} on a machine that has Python on it. Where does
\pkg{httpx} end up, and which of the things you might run afterwards can see
it?

The honest answer is that you cannot know without looking, and that is the
point. There is no single place. \code{pip} installs into whichever
interpreter invoked it, and which interpreter that is depends on your
\code{PATH}, on whether an environment is active in this shell, and on what
your operating system's package manager did to \code{/usr/bin} years ago.

So this book never asks you to know. It asks the interpreter:

\pyfile{code/ch02/where_am_i.py}{An environment, described by the interpreter that is in it}{lst:ch02-where}

\noindent
Run from \code{code/}, that prints:

\transcript{ch02-where-am-i}

\noindent
Four facts, and each of them is a directory question. \code{sys.prefix} is the
environment's root; \code{sys.base\_prefix} is the root of the interpreter the
environment was built from. When they differ you are in a virtual environment,
and that comparison is the whole test \dash{} there is nothing else to check.
The interpreter is inside the directory. The third-party package is inside it
too, under \code{site-packages}. The standard library is not, because it ships
with the interpreter and has never been anybody's dependency.

\begin{csbox}
\code{.venv/} is closest to \code{obj/} and \code{bin/} together: build output,
per project, safe to delete, never committed. The difference that matters is
that deleting \code{obj/} costs you a rebuild and deleting \code{.venv/} costs
you nothing at all, because \code{uv sync} rebuilds it from a file you did
commit. Treat it as disposable and you will be right every time.
\end{csbox}

\begin{trapbox}
\textbf{\code{pip install} puts the package on the machine, like a global
tool.} It does not, and the version of this belief that survives longest is
the dangerous one: that it does not much matter which interpreter gets it.
Install into the system interpreter and you have changed a dependency of your
operating system's own scripts. Install into the wrong project's environment
and a colleague's clean checkout will not run your code, with no error message
anywhere that names the cause. The rule that removes the whole class:
\textbf{never run \code{pip install} in this book.} Dependencies go into
\code{pyproject.toml} with \code{uv add}, and environments are built from the
lockfile.
\end{trapbox}

\section{Two files, and only one of them is the truth}
\label{sec:ch02-two-files}
\index{packaging!pyproject.toml}
\index{packaging!lockfile}

\noindent
\code{pyproject.toml} is the project file, and this book's own is the skeleton
the brief promised you. Here is the part that says what the code needs in order
to run:

\pyregion{code/pyproject.toml}{project}{The \code{[project]} table: what this project needs to run}{lst:ch02-project}

\noindent
And, separately, what you need in order to work on it:

\pyregion{code/pyproject.toml}{groups}{Dependency groups: what you need to work on it, which is not the same list}{lst:ch02-groups}

\noindent
That split is the first thing to steal. \code{[project].dependencies} is what
a deployment installs; a dependency group is not installed unless something
asks for it. A container image built from the first list does not contain a
test runner, a linter or a type checker, and it does not contain them because
of where the line is written rather than because somebody remembered to prune
them afterwards.

\begin{csbox}
\code{pyproject.toml} is \code{.csproj}: the project's identity, its
dependencies, and the configuration of every tool that acts on it. It is TOML
rather than XML and it holds far more \dash{} \pkg{ruff}, \pkg{pytest},
\pkg{pyright} and \pkg{mypy} are all configured in this one file, so a Python
repository has nothing corresponding to the scatter of
\code{.editorconfig}, \code{Directory.Build.props} and a ruleset.
\end{csbox}

\noindent
Now the second question, and again answer it before reading on. This project
declares the dependencies you have just seen in two short lists. When
\code{uv sync} finishes, how many distributions are in \code{.venv}?

\pyfile{code/ch02/lockfile.py}{Counting what was declared against what was resolved}{lst:ch02-lockfile}

\transcript{ch02-lockfile}

\noindent
Most of the environment was never named by anybody. Those are the transitive
dependencies \dash{} what \pkg{fastapi} needs, what \pkg{anthropic} needs,
what those need in turn \dash{} and the file that pins them to exact versions
is \code{uv.lock}, which is committed. That is the distinction the rest of the
chapter rests on: \code{pyproject.toml} records an \emph{intention} and
\code{uv.lock} records a \emph{result}. Only one of them can be used to
reproduce an environment.

\begin{csbox}
\code{uv.lock} is \code{packages.lock.json}, and the argument for committing
it is the one you already accept. The difference is cultural rather than
technical: locking is opt-in and uncommon in .NET, and in Python
\code{uv.lock} is written by default the first time you run anything, so the
only way to end up without one is to add it to \code{.gitignore} on purpose.
\end{csbox}

\begin{trapbox}
\textbf{\code{requirements.txt} is the lockfile.} It is a wish list, and
usually a partial one. It is a file some person wrote, typically naming only
the packages they thought of, typically with ranges rather than exact
versions, and nothing checks it against what is installed. Two machines
following the same \code{requirements.txt} routinely end up with different
versions of most of what they are running, and the failure appears weeks
later as a bug that reproduces on one of them. \code{uv.lock} is generated,
covers the whole graph, records a hash for every artefact, and
\code{uv sync --locked} refuses to install anything else.
\end{trapbox}

\mermaidfig{declare-resolve-lock}{Declared, resolved, installed: three files and which one reproduces an environment}{declare, resolve, lock}

\begin{exercise}{e02_01_pinned_version}{Read the lock, not the wish list}
The starter has one function to finish: given a parsed \code{uv.lock} and a
distribution name, return the exact version it is pinned to. The tests drive
it with this book's own lockfile, so one of them asks for a package that
appears in no dependency list anywhere in the repository \dash{} and expects
you to find a version for it anyway. That test is the chapter in one
assertion.
\end{exercise}

\section{Run it, do not activate it}
\label{sec:ch02-run}
\index{packaging!uv run}

\noindent
Every tutorial you will read tells you to activate the environment. The
instinct that makes a .NET engineer comfortable with that is worth
interrogating before you adopt it: which of the things that will run your code
tomorrow are going to execute that activation step?

A shell you opened, and nothing else. Activation edits \code{PATH} in one
process. A second terminal has not run it. A \code{Makefile} target has not run
it. \code{cron} has not run it. CI has not run it, and neither has your
editor's test runner, which is why a test suite that passes in the terminal and
fails in the IDE is so often this and nothing more interesting.

The whole of this book's workflow is three commands, none of which needs an
environment to be active:

\begin{shellcmd}
uv init --name incident-tools   # a project, with a src/ layout
uv add httpx                    # a dependency, written into pyproject.toml
uv run python -m incident_tools # and run it, in the right environment
\end{shellcmd}

\noindent
\code{uv run} reads \code{pyproject.toml} and \code{uv.lock}, makes sure
\code{.venv} matches them, and then runs your command inside it. It does that
on every invocation, which is why it is correct from a shell, from a
\code{Makefile}, from \code{cron} and from CI with nothing to remember and
nothing to set up. \code{uvx} is its sibling for a tool you want to run and
not depend on \dash{} the equivalent of \code{dotnet tool}, without the
install step.

\begin{csbox}
\code{uv run} is \code{dotnet run}, and it restores before it runs for the
same reason. \code{uv add} is \code{dotnet add package}. The one with no
counterpart is activation, and that is because .NET never needed it: there is
nothing to activate when the environment is a machine.
\end{csbox}

\begin{trapbox}
\textbf{I activate the environment and then run things.} The habit is not
wrong so much as unreliable, and it fails in the direction that is hardest to
debug: it works on your machine. Activation is per shell, so the failures land
in the places you cannot watch \dash{} the scheduled job, the build agent, the
colleague's first checkout. Type \code{uv run} in front of the command instead
and the question of which environment you are in stops existing.
\end{trapbox}

\begin{warning}
\code{uv run} and \code{uv sync --locked} do different things to a lockfile
that has fallen behind \code{pyproject.toml}, and the difference is the one
worth knowing. Add a dependency by hand, then run \code{uv sync --locked}: it
exits non-zero and tells you the lock needs updating. Run \code{uv run}
instead and it re-locks, installs and carries on without comment. That is
convenient at your desk and wrong in CI, where the entire point is to fail
rather than silently install something nobody reviewed. Use
\code{uv sync --locked} in every automated context.
\end{warning}

\section{What uv buys, measured}
\label{sec:ch02-measured}
\index{measurement!E2}

\noindent
That \pkg{uv} is fast is the first thing anybody says about it, and it is not
by itself a reason to adopt a tool. The question worth answering is
\emph{where the time goes}, because that is what decides whether configuring a
cache in CI is worth an afternoon.

So: this book's own lockfile, exported so that both tools install exactly the
same \val{e2.packages} distributions with no resolution to do, onto the pinned
interpreter, each with a private package cache that is emptied before a cold
trial and kept for a warm one. The environment is created inside the timed
region in both cases, because with \code{pip} that means \code{python -m venv}
and a reader is buying the whole journey from checkout to runnable. Median of
\val{e2.trials} trials.

\begin{center}
\small
\begin{tabularx}{\linewidth}{@{}Xrrr@{}}
\toprule
& \textbf{cold cache} & \textbf{warm cache} & \textbf{what the cache buys} \\
\midrule
\code{uv sync --locked} & \val{e2.uv.cold}\,s & \val{e2.uv.warm}\,s & \val{e2.uv.cachegain}$\times$ \\
\code{pip install -r} & \val{e2.pip.cold}\,s & \val{e2.pip.warm}\,s & \val{e2.pip.cachegain}$\times$ \\
\midrule
\textbf{ratio} & \val{e2.cold.ratio}$\times$ & \val{e2.warm.ratio}$\times$ & \\
\bottomrule
\end{tabularx}
\end{center}

\noindent
The last column is the finding, and it is not the one the headline suggests. A
populated cache buys \pkg{uv} a factor of \val{e2.uv.cachegain}; it buys
\code{pip} almost nothing at all. \code{pip}'s time is not the download. It is
\code{pip}'s own work \dash{} building the environment, unpacking wheels,
copying files \dash{} and no cache removes any of it, which is why
\code{pip}'s warm figure is within a rounding of its cold one. \pkg{uv} writes
its warm installs by linking from the cache rather than copying, so once the
wheels are local there is very nearly nothing left to do.

Two consequences you can act on. Caching the package directory in CI is worth
doing with \pkg{uv} and close to pointless with \code{pip}. And a container
build that installs with \code{pip} pays the same cost on every layer rebuild
however good your caching is.

\begin{note}
\textbf{What these numbers are, and what they are not.} The ratios are the
transferable half; the seconds are one machine on one afternoon, and the
machine that ran them has a slow and unreliable network. \code{pip}'s three
cold trials landed between \val{e2.pip.cold.best} and
\val{e2.pip.cold.worst} seconds, which is tight. \pkg{uv}'s best cold trial
was \val{e2.uv.cold.best} seconds and its worst was \val{e2.uv.cold.worst}
\dash{} a download that stalled for over five minutes. That is a property of
the link and not of the tool, it is why a median rather than a mean is
reported, and it is why a cold number is the least transferable figure in the
table. The script is \code{code/measure/e2\_install.py} and the raw trials are
committed beside it; run it yourself and expect different seconds and similar
ratios. \code{pip} was version \valtext{e2.pip.version}, the one that ships
with the pinned interpreter.
\end{note}

\section{The skeleton you can copy}
\label{sec:ch02-skeleton}
\index{packaging!src layout}
\index{packaging!ruff}

\noindent
\code{uv init} gives you a project whose package sits under a \code{src/}
directory rather than at the repository root, and the reason is worth a
paragraph
because it looks like ceremony and is not. If your package sits at the root it
is importable from the root whether or not it has been installed, so your tests
pass against the files on disk and tell you nothing about whether the thing you
ship would work. Under \code{src/} it has to be installed to be importable,
which means your tests run against the installed artefact. It is the difference
between testing your source tree and testing your package.

\code{uv init} also writes an entry point: a name in \code{[project.scripts]}
bound to a function, which becomes a command on the path once the project is
installed. That is the \code{Program.cs} of a Python project, except that a
project can declare several and each is one line.

\begin{csbox}
There is no \code{Program.cs} and no \code{Main} in Python. A module that
should be runnable ends with \code{if \_\_name\_\_ == "\_\_main\_\_":}, which
is the topic of Chapter~\ref{ch:runtime}; a package that should install a
command declares it in \code{[project.scripts]}. The two are independent and
most projects want both.
\end{csbox}

\noindent
The last piece is the linter. \pkg{ruff} replaces the analysers and
\code{dotnet format} at once \dash{} one tool, configured in
\code{pyproject.toml}, that both reports and fixes \dash{} and it is fast
enough that there is no reason not to run it on every save. \pkg{pre-commit}
is what makes it unavoidable for everybody else: a git hook, declared in a
file, that runs the formatter and the linter over the files a commit touches
and refuses the commit if they are unhappy. Nothing in .NET does this because
nothing in .NET needs to.

\begin{exercise}{e02_02_install_set}{What does a deployment actually install?}

installed? One test drives it with a small document that carries every shape a
requirement can take; the last one asks this book's own project whether a
deployment of it would contain \pkg{pytest}.
\end{exercise}

\noindent
You now have an environment you can trust and a way to rebuild it from a file.
That is the floor every remaining chapter's listings stand on. The next one is
about a different kind of trust: Chapter~\ref{ch:typing} is where your instinct
that a type annotation means something meets a runtime that never checks one.
