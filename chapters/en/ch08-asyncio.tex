\chapter{asyncio for people who know \texorpdfstring{\code{Task}}{Task}}
\label{ch:asyncio}
\index{asyncio}
\index{asyncio!coroutine}

\noindent
You have written this code before. You have awaited a call, run a batch of
them together, cancelled one on a deadline, and been paged at four in the
morning because something in the middle of it blocked. The concepts all
transfer, the names mostly transfer, and the residue that does not transfer
is where every asyncio incident in this book comes from.

So this chapter is a translation, not an introduction. It assumes the
mental model you already have and spends its length on the five places
that model is wrong \dash{} each one a place where the Python runs, does
not raise, and does something other than what a .NET engineer would swear
it does.

\section{What transfers}
\label{sec:asyncio-map}
\index{asyncio!translation table}

Almost all of it. The table is the chapter in one page; the rest of the
chapter is the five rows that lie.

\small

\noindent
Two rows say \emph{nothing}, and they are the two that matter most.
\code{SynchronizationContext} has no Python equivalent at all, so there is
nothing to capture, nothing to configure away, and no way to deadlock a
request by reading \code{.Result} on it. That whole family of .NET bug reports simply
does not exist here. What you get instead is one thread, and
\S\ref{sec:asyncio-one-thread} is what that costs.

\begin{note}
The companion volume on LangChain and LangGraph owns the event loop,
cancellation and the concurrency measurements in depth; its Chapters~3
and~4 are where to go when you want the mechanism rather than the
translation. This chapter does not repeat a section of it.
\end{note}

\section{Cold, not hot}
\label{sec:asyncio-cold}
\index{asyncio!coroutine}
\index{asyncio!create\_task@\texttt{create\_task}}

In C\#, by the time a method returns you a \code{Task}, the work is
already under way. The \code{Task} is a handle on something running.
Awaiting it is how you collect the answer, and you can await it twice and
get the same answer twice.

A Python coroutine is not that. Calling a coroutine function runs nothing
at all: it builds an object and hands it back, and the body does not
execute until somebody awaits it or gives it to the loop. Before you read
on, decide what each of the four steps in the next listing prints.

\pyfile{code/ch08/cold.py}{A coroutine is cold, and a Task is not}{lst:ch08-cold}

\transcript{ch08-cold}

\noindent
Three of those are worth having in your fingers. \api{create\_task}
schedules rather than starts, so the body has still not run when it
returns \dash{} it runs when the caller next gives the loop a chance.
Forgetting the \code{await} altogether is a \emph{warning}, printed when
the object is collected, and not an error: the call did nothing and the
program carried on. And awaiting a coroutine twice raises, because the
coroutine \emph{is} the work rather than a handle on it.

\mermaidfig{async-cold-coroutine}{Nothing runs until the loop is given a chance: the two steps a C\# \code{Task} has already taken by the time you hold one}{a coroutine's three steps}

\begin{trapbox}
\textbf{A coroutine is a \code{Task}, so calling it starts it.} It is not
and it does not. In C\# a forgotten \code{await} still runs the work and
loses the result; in Python it runs nothing and says so in a warning you
will not see on a busy stderr. The two failures look alike in a code
review and are opposites at run time.
\end{trapbox}

\begin{exercise}{e08_01_schedule}{Make three coroutines overlap}
Three names, three fetches, one result list in the order the names were
given \dash{} and all three in flight at once. The test does not time
anything: it watches how many fetches are running simultaneously, so an
implementation that awaits each one as it builds it returns the right
answers and still fails.
\end{exercise}

\section{One loop, one thread}
\label{sec:asyncio-one-thread}
\index{asyncio!event loop}
\index{asyncio!blocking call}

Here is the rest of the bargain for losing the \code{SynchronizationContext}.
Your ASP.NET request ran on a thread pool: when one thread blocked, the
others carried on and the pool grew another. An event loop is one thread
running one coroutine at a time, and it takes the next one only when the
current one reaches an \code{await}. A call that blocks never reaches one.

That much most people know. The part a thread pool hides is what happens
with more than one offender, which is what experiment~E4 measures: the
listing below is the same shape, for you to run.

\pyfile{code/ch08/one_loop.py}{Where a slow call spends its time decides who else pays}{lst:ch08-one-loop}

\noindent
\val{e04.offenders} coroutines each taking \val{e04.block.ms}~ms, beside
\val{e04.innocent} that merely await \val{e04.wait.ms}~ms. In .NET those
four would land on four pool threads and overlap, finishing in about
\val{e04.block.ms}~ms between them, and nothing else in the process would
notice. On one thread they cannot overlap with each other either: they
serialise, taking \val{e04.serial.ms}~ms, and every one of the
\val{e04.innocent} bystanders waits for all four. E4, over the median of
\val{e04.trials} trials, asserts that the worst bystander's latency grows
by at least \val{e04.added.floor.ms}~ms, and that moving the same calls off
the loop with
\api{asyncio.to\_thread} keeps the growth under
\val{e04.threaded.ceiling.ms}~ms.

\mermaidfig{async-one-thread}{The queue moves only when the running coroutine reaches an \code{await}}{one thread, one queue}

\begin{csbox}
\api{to\_thread} is \code{Task.Run}, with a much smaller pool behind it:
the loop's default executor holds \code{min(32, cpu\_count + 4)} threads
and does not grow the way the .NET pool does. It is right for a blocking
call that \emph{waits} and wrong for a thousand of them at once, and it is
the wrong tool entirely for work that burns CPU \dash{} that wants a
process pool, for the reason Chapter~\ref{ch:runtime} gives.
\end{csbox}

\begin{trapbox}
\textbf{\code{.Result} deadlocks, so I use \code{ConfigureAwait(false)}.}
Neither exists here and neither is needed. The failure that replaces them
is quieter: one blocking call inside one coroutine freezes every other
coroutine on the loop, with no exception, no log line and nothing in a
trace to say which one did it.
\end{trapbox}

\begin{exercise}{e08_02_unblock}{Get a blocking call off the loop}
A synchronous function you do not own and cannot rewrite, called from a
coroutine. Return exactly what it returns without the loop going quiet.
The test runs a heartbeat coroutine alongside and counts its ticks,
because a blocked loop cannot tick.
\end{exercise}

\section{WhenAll, twice}
\label{sec:asyncio-whenall}
\index{asyncio!gather@\texttt{gather}}
\index{asyncio!TaskGroup@\texttt{TaskGroup}}

Python spells \code{Task.WhenAll} two ways, and everything written before
2022 uses the first. They are the same speed. They differ in exactly one
respect, and it is what happens to the \emph{siblings} of a coroutine that
raises.

\pyfile{code/ch08/whenall.py}{The same batch, failing the same way, twice}{lst:ch08-whenall}

\transcript{ch08-whenall}

\noindent
Read the first three lines again. The caller handled the error and moved
on, and then the sibling printed \dash{} it was still running, with nobody
waiting for it and nobody holding a reference to its result. In a service
that is a connection still open, a transaction still uncommitted and a
retry that fires after the request it belonged to has returned a 500.
\api{TaskGroup} cancels the siblings instead, and reports the failures as
an \code{ExceptionGroup}, which is the closest thing Python has to
\code{AggregateException} and is Chapter~\ref{ch:errors}'s subject.

\begin{trapbox}
\textbf{\api{gather} is \code{Task.WhenAll}.} It is \code{WhenAll} without
the part where the failure stops the batch. Choose between them on failure
semantics, never on speed: they do not differ on speed, and anybody who
tells you \api{TaskGroup} is faster is quoting a difference that is not
there.
\end{trapbox}

\begin{exercise}{e08_03_when_all}{Port a WhenAll with a CancellationToken}
The starter carries the three-line C\# original: a
\code{CancellationTokenSource} with a budget, a \code{Select} into a batch
of tasks, one \code{WhenAll}. Port it so that the results keep their
order, one budget covers the whole batch, and nothing is left running when
the budget runs out. The last of those is the one \api{gather} will not
give you.
\end{exercise}

\begin{exercise}{e08_04_bounded}{Bound the concurrency}
\api{gather} and \api{TaskGroup} both start everything at once. Twenty
requests against a service that tolerates four is a load test with your
own name on it. Keep the results in order and never have more than
\code{limit} in flight.
\end{exercise}

\section{Cancellation is an exception}
\label{sec:asyncio-cancel}
\index{asyncio!cancellation}
\index{asyncio!CancelledError@\texttt{CancelledError}}

A \code{CancellationToken} is a flag you are given, pass down and poll. It
is cooperative in the sense that a method which never checks it never
stops.

Python's cancellation is cooperative in a different sense.
\api{task.cancel()} does not stop anything by itself: it records the
request and returns, and at the cancelled coroutine's next \code{await} a
\api{CancelledError} is raised \emph{inside} it. There is no token to
pass, no parameter to thread through twenty call sites, and nothing to
poll. There is also nothing you can do about a coroutine that never
awaits.

Which means cancellation obeys the same rules as any other exception \dash{}
including the rule that whoever catches it owns it. Four tasks below are
cancelled identically and each guards itself differently. Decide which of
them survive before you read the output.

\pyfile{code/ch08/cancelled.py}{Four ways to meet a cancellation, three of them wrong}{lst:ch08-cancelled}

\transcript{ch08-cancelled}

\noindent
If you predicted that \code{except Exception} swallows it, you are in
good company and you are wrong, and the first line of the output says why:
\api{CancelledError} inherits from \code{BaseException} directly and never
passes through \code{Exception} at all. The broad clause that a .NET
engineer has been trained to treat as the reckless one is the safe one
here. What swallows a cancellation is \code{except BaseException}, a bare
\code{except:}, and \dash{} far more often in real code \dash{} an
\code{except asyncio.CancelledError} block that does its cleanup and
forgets to re-raise.

\mermaidfig{async-cancel-path}{Cancellation is delivered, not polled, and the clause that stops it is not the one you would expect}{how a cancellation travels}

\begin{csbox}
A bare \code{raise} at the end of an \code{except} block is \code{throw;}
\dash{} it continues the exception already in flight, traceback intact.
\code{raise e} is \code{throw e;} and resets it. Chapter~\ref{ch:errors}
makes the distinction properly; here it is the whole fix.
\end{csbox}

\begin{trapbox}
\textbf{Cancellation is a token I poll, so catching \code{Exception} is
how I lose it.} Backwards, in both halves. Cancellation arrives as an
exception at an \code{await}, and \code{except Exception} is precisely the
clause that lets it through. The line to search your codebase for is not
\code{except Exception}; it is \code{except asyncio.CancelledError}
without a \code{raise} under it.
\end{trapbox}

\begin{exercise}{e08_05_cancel_safe}{Clean up and stay cancellable}
The starter releases its lease when cancelled and is still wrong: it
reports success to whoever cancelled it. Release the lease and let the
cancellation continue. One of the three tests checks the consequence a
caller actually meets, and it is in the next section.
\end{exercise}

\section{Deadlines, and a client that has one}
\label{sec:asyncio-deadline}
\index{asyncio!timeout@\texttt{timeout}}
\index{timeout}

\code{CancelAfter} on a token source arms a deadline that cancels the work
when it passes. \api{asyncio.timeout} does the same job and looks nothing
like it: it is a context manager, it covers a block rather than a token,
and the exception it raises is not the one the work inside it saw.

\pyfile{code/ch08/deadline.py}{A deadline is a cancellation with a better name at the boundary}{lst:ch08-deadline}

\transcript{ch08-deadline}

\noindent
The body sees a \api{CancelledError}, because a deadline cancels; the
caller sees a \code{TimeoutError}, because the context manager converts it
on the way out. That conversion is why the previous section's missing
\code{raise} is worse than it looks. Line four is a body that swallowed
the cancellation its own deadline sent: the block then exits normally and
\emph{no} \code{TimeoutError} is raised at all. A timeout that silently
does not fire is a harder incident to read than one that does.

The last two lines are the client, read off the installed \pkg{httpx}
rather than written down. A default \api{httpx.AsyncClient} already
carries a deadline, it is five seconds, and it applies to four phases
separately rather than to the request as a whole.

\begin{trapbox}
\textbf{\code{HttpClient} is a singleton, so \api{AsyncClient} is too.}
The lifetime advice carries \dash{} construct it once, share it, close it
\dash{} and the defaults do not. Where your \code{HttpClient} has one
timeout covering the whole request and a value long enough that you have
probably never set it, \api{AsyncClient} has four short ones, and the
first hard afternoon in a new Python service is usually a read timeout
nobody configured.
\end{trapbox}

\section{The sync boundary}
\label{sec:asyncio-boundary}
\index{asyncio!asyncio.run@\texttt{asyncio.run}}

C\# lets \code{Main} be \code{async} and the runtime awaits it for you.
Python has no such entry point: \code{await} outside a function is a
syntax error, so something synchronous has to start the loop. That
something is \api{asyncio.run}, called once, at the top, and never from
inside a coroutine.

\pyfile{code/ch08/boundary.py}{Where async code starts, and what cannot cross}{lst:ch08-boundary}

\transcript{ch08-boundary}

\noindent
The second line is the \code{.Result} habit meeting a runtime that does
not have it. Asking an unfinished \api{Task} for its value does not block
and cannot deadlock: it raises. There is no blocking wait on a task from
inside the loop, which is the same fact as \S\ref{sec:asyncio-one-thread}
seen from the other side \dash{} a blocking wait would stop the thread
that is supposed to complete the thing being waited for.

\medskip
\noindent
Three incidents, then, and each is now something you can recognise on a
page rather than at four in the morning. A blocking call, which freezes
every coroutine beside it and appears in no log. An orphaned task, which
\api{gather} leaves running after its batch has failed. And a swallowed
\code{CancelledError}, which turns a cancelled task into a successful one
and a deadline into a promise nothing keeps. None of the three raises, and
all three are visible in a review once you know the shapes.
